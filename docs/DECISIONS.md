# 결정 기록

갈림길이 있었던 지점마다 **무엇을 골랐는지 / 왜 골랐는지 / 무엇을 왜 버렸는지**를 적었습니다.
작업 전에 네 가지 방향을 먼저 확인받고 코드를 썼습니다. 아래에서 *(사전 확인)* 표시가 그 넷입니다.
`이런 서체`로 표시한 것은 전부 코드에 실제로 그 이름으로 존재합니다.

---

## 0. 용어

파티클 하나는 정점 하나이고, 화면에서는 작고 흐릿한 원으로 보입니다.
정점의 화면 위치를 계산하는 것이 **정점 셰이더**, 그 정점이 덮는 픽셀 색을 계산하는 것이 **프래그먼트 셰이더**입니다.

| 용어 | 뜻 |
| --- | --- |
| **프레임 타임** | 화면 한 장을 만드는 데 걸린 시간. 60fps면 한 장에 16.7ms |
| **유니폼** | 셰이더에 넘기는 값 중 모든 파티클이 함께 쓰는 값(색, 중력 등). 바꾸는 비용이 거의 0 |
| **어트리뷰트** | 파티클마다 다른 값(위치 등). 파티클 수만큼 메모리를 쓴다 |
| **버퍼** | 어트리뷰트를 담는 배열. CPU 쪽 내용을 GPU로 복사(업로드)해야 화면에 반영된다 |
| **드로우 콜** | GPU에 보내는 그리기 명령 한 건. 이 과제는 이펙트의 드로우 콜을 항상 1건으로 유지하는 것이 하드 제약 |
| **합성 방식** | 이미 그려진 화면 위에 새 픽셀을 얹는 방법. **가산**은 색을 더해 밝아지고, **일반**은 투명도로 섞는다 |
| **오버드로우** | 같은 픽셀을 여러 번 칠하는 것. 반투명 파티클이 겹칠수록 심해지고, GPU 부담의 주원인 |
| **픽셀 밀도** | 논리 픽셀 하나를 실제 픽셀 몇 개로 그릴지. 2면 칠할 픽셀이 4배. 코드에서는 `devicePixelRatio` |
| **적분** | 속도로 위치를 옮기는 계산. 매 프레임 `위치 += 속도 × dt`를 파티클 전부에 반복. `dt`는 흐른 시간(초) |
| **p95** | 프레임 100개를 느린 순으로 줄 세웠을 때 위에서 5번째 값. 평균에 묻히는 "가끔 튀는 프레임"을 드러낸다 |
| **가비지 컬렉션** | 안 쓰는 객체를 브라우저가 치우는 작업. 치우는 동안 멈추므로 그 프레임만 튄다 |

비용은 "파티클 수와 무관하게 일정"과 "파티클 수에 비례"를 구분해서 씁니다.

## A. 이펙트 모듈 내부

### A-1. 파티클 슬롯 관리 — 링 버퍼

**문제** 슬롯을 미리 잡아두고 재사용해야 합니다. 새 파티클에 빈 슬롯을 내주고 수명이 다한 슬롯을 회수하는 일이 매 프레임 수백 번 일어납니다.

**선택** 원형으로 도는 고정 좌석. `head`는 가장 오래된 파티클의 자리, `span`은 거기서부터 살아있는 개수입니다.
새 자리는 살아있는 구간 바로 뒤(`(head + span + i) % capacity`)에서 내주고, 회수는 구간 앞쪽부터 밀어냅니다.

**근거**

- 할당과 "가장 오래된 것 회수"가 둘 다 상수 시간입니다. 둘을 동시에 만족하는 구조는 이것뿐이었습니다.
- 태어난 순서가 슬롯 순서와 일치하므로 가장 오래된 것을 찾을 필요가 없습니다. `head`가 답입니다.
- 살아있는 슬롯이 항상 한 덩어리라, GPU로 복사할 구간이 많아야 두 조각입니다.

**고르지 않은 대안**

| 대안 | 탈락 사유 |
| --- | --- |
| **빈자리 메우기** (죽으면 맨 뒤 파티클을 그 구멍으로 옮김) | 정점 계산량은 더 적지만, 자리를 옮기는 순간 태어난 순서가 뒤섞여 "가장 오래된 것 회수"가 전체 탐색이 됩니다. 버퍼의 아무 곳이나 고쳐 쓰게 되어 복사 구간도 조각납니다 |
| **빈자리 목록** (죽은 슬롯 번호를 따로 모아둠) | 슬롯 순서가 완전히 무작위가 되어 복사 구간이 슬롯 단위로 쪼개집니다 |

### A-2. 드로우 콜 1건 유지 — 그리기 범위를 상황에 맞게 좁힘

**문제** 매 프레임 "용량 전체를 그려라"라고 한 번 명령하면 쉽지만, 파티클이 500개일 때도 GPU가 정점 5,120,000개를 계산합니다.

**선택** 살아있는 구간이 배열 끝을 넘지 않으면 그 구간만(`setDrawRange(head, span)`), 끝을 넘어 0번으로 돌아간 프레임에만 전체를 그립니다.
어느 쪽이든 명령은 한 건입니다.

**고르지 않은 대안**

| 대안 | 탈락 사유 |
| --- | --- |
| **항상 전체를 그림** | 코드는 두 줄 짧지만 부하가 낮을 때 만 배 낭비를 감수합니다 |
| **끝을 넘어간 프레임만 명령 2건** | 정점 계산량이 항상 살아있는 개수만큼이라 성능상 최선입니다. "드로우 콜 항상 1건" 제약 때문에 택하지 않았습니다. 성능이 문제가 되면 제일 먼저 풀 매듭입니다. 대가는 README "알려진 한계"에 실측치로 남겼습니다 |

### A-3. 적분 — 속도를 먼저 갱신하고, 감쇠는 지수 함수로

**선택** 속도를 먼저 갱신하고 그 새 속도로 위치를 옮깁니다(준음함수 오일러 적분).
감쇠는 `속도 = 속도 × exp(-감쇠계수 × dt)`입니다.

**근거** 파티클끼리 상호작용이 없어 더 정밀한 계산법을 써도 화면에서 차이가 없습니다.
지수 함수를 쓰면 `dt`가 상한(0.1초)까지 튀어도 속도의 부호가 뒤집히지 않습니다.

**고르지 않은 대안**

| 대안 | 탈락 사유 |
| --- | --- |
| **`속도 × (1 - 감쇠계수 × dt)`** | `감쇠계수 × dt`가 1을 넘으면 괄호 안이 음수가 되어 파티클이 뒤로 날아갑니다. 현재 값(1.9, 0.1초)에서는 안전하지만 여유가 두 배뿐입니다. 지수 함수는 프레임마다 한 번만 계산하므로 비용이 사실상 0입니다 |
| **룽게–쿠타 4차** | 계산량 3배에 화면 차이 없음 |

### A-4. 파티클 모양 — 셰이더로 직접 그림, 이미지 없음

**선택** 프래그먼트 셰이더에서 `gl_PointCoord`로 중심 거리를 계산해 가장자리가 부드러운 원을 만듭니다.

**근거** 소유권 문제입니다. 이미지를 불러 쓰면 로드 실패 처리, 보유 주체, 두 씬 공유 시 해제 주체가 한꺼번에 따라옵니다.
"모듈이 만든 GPU 자원은 모듈이 치운다"는 규칙과 정면으로 걸립니다. 덤으로 확대해도 깨지지 않고 저장소에 이미지가 없습니다.

**고르지 않은 대안** 스프라이트 시트. 불규칙한 파편이나 연기 얼룩을 못 만드는 것이 대가입니다. 필요하면 셰이더 노이즈가 이미지보다 쌉니다.

### A-5. `THREE.Points` — 파티클 하나를 점 하나로

**근거** 파티클당 정점 1개. 사각형 판 방식은 정점 4개에 연결 정보까지 필요해 4배입니다.

**고르지 않은 대안** `InstancedMesh`. 회전과 임의의 텍스처 좌표가 가능하지만 이 이펙트에는 회전이 필요 없습니다.
점 하나의 화면 크기에는 GPU 상한(보통 1024픽셀)이 있어 거기 걸리면 갈아타야 하고, 그 교체가 씬에 안 보이도록 `Object3D`로 내줬습니다(B-2).

### A-6. GPU 업로드 — 살아있는 구간만

**선택** 매 프레임 `[head, head+span)` 구간만 복사합니다(`addUpdateRange`). 스폰 초기값은 터진 프레임에만 복사합니다.

**근거** 용량 5,120,000을 매 프레임 전부 복사하면 초당 6GB가 넘습니다. 실제로 바뀐 값은 그중 일부입니다.

**주의했던 점** 복사 구간은 `head`를 밀기 **전** 기준으로 잡아야 합니다.
이번 프레임에 죽은 슬롯의 "수명 0"을 GPU에 못 올리면, 링이 한 바퀴 돌아 전체를 그리는 순간 그 슬롯이 유령 파티클로 남습니다.
순서를 반대로 잡았다가 발견하고 고쳤습니다.

### A-7. 난수 — 고정 시드 선형 합동 생성기

**선택** `Math.imul(s, 1664525) + 1013904223`. 시드를 고정합니다.

**근거** 측정을 두 번 돌렸는데 파티클 분포가 매번 다르면, 프레임 시간 차이가 코드 때문인지 우연 때문인지 구분할 수 없습니다.
헤드리스 벤치의 생존 수와 draw 슬롯이 재실행해도 한 자리까지 같은 것이 이 선택의 증거입니다.

**고르지 않은 대안** `Math.random()`(재현 불가), mulberry32(품질은 더 좋지만 계산량 2배. 흩뿌리는 용도에서 차이가 눈에 안 띕니다).

## B. 공개 API

### B-1. 설정을 두 층으로 — 기준은 "버퍼를 다시 잡아야 하는가"

**선택**

- 생성 시 고정: 용량, 버스트당 개수, 오버플로 정책, 시드. 읽기 전용이고 setter가 없습니다.
- 런타임 변경: 색, 크기, 수명, 속력, 중력, 감쇠, 합성 방식. `setStyle()` 하나로.

**근거** "자주 바꾸나"는 경계가 흐리지만 "버퍼를 다시 잡아야 하는가"는 둘 중 하나로 갈립니다.
바꿀 수 있는 13개 항목이 전부 유니폼이나 적분 계수로 흡수되고 버퍼를 건드리는 게 없다는 사실이 증거입니다.

**고르지 않은 대안** 전부 열어두고 내부에서 재할당. 프레임 도중 대형 버퍼 재할당이 숨고, 호출하는 쪽이 비용을 예측할 수 없습니다.

### B-2. 이펙트를 `Points`가 아니라 `Object3D`로 내줌

**근거** 내부를 점 → 사각형 판 → GPU 적분으로 갈아끼워도 씬 코드가 바뀌지 않습니다.
`Points`로 내주면 누군가 `.geometry.attributes.position`을 만지기 시작하고, 그 순간 교체가 불가능해집니다.

### B-3. 통계 객체는 하나를 재사용

**근거** 매 프레임 읽힙니다. 읽을 때마다 새 객체를 만들면 초당 60개의 쓰레기가 쌓이고, 가비지 컬렉션이 우리가 재려는 프레임 시간에 찍힙니다.
측정 도구가 측정 대상을 바꾸면 안 됩니다.

**대가** 값을 보관하려면 직접 복사해야 합니다. 타입 주석에 명시했습니다.

### B-4. 발사 지점은 받은 객체에 채워 넣기 (불변성 규칙의 의도적 예외)

**근거** B-3과 같습니다. 최대 부하에서 초당 1,481번 호출되므로 좌표 객체가 초당 2,962개 생겼다 버려집니다.
불변성 규칙의 목적은 숨은 부작용을 막는 것인데, 여기서 건네받은 객체는 호출마다 통째로 덮어쓰는 출력용 그릇이라 공유 문제가 없습니다.

## C. 하네스와 소유권

하네스는 씬과 이펙트를 굴리는 바깥 껍데기(`src/core/App.ts`)입니다.

### C-1. 이펙트는 하네스가 하나만 갖고 두 씬이 공유

**근거** 씬마다 하나씩 두면 전환할 때마다 약 205MB의 버퍼를 새로 잡고, 전환 프레임이 수십 ms 튑니다.

**대가** 전환 순간 날아가던 파티클이 새 씬으로 딸려 옵니다. 최대 수명 1.4초 안에 사라집니다.

**부수 효과** `Object3D`는 부모가 하나뿐이라 새 씬에서 `add()` 한 번이면 이전 씬에서 자동으로 빠집니다. `remove()`도, 씬 쪽 "떼어내기" 함수도 필요 없습니다.

### C-2. 이월 파티클의 색 — 즉시 새 씬 것으로 *(사전 확인)*

**근거** 파티클당 추가 메모리 0. 대가는 전환 순간 색이 한 번 튀는 것뿐입니다.

**고르지 않은 대안**

| 대안 | 탈락 사유 |
| --- | --- |
| **파티클마다 색 어트리뷰트** | 옛 색을 유지할 수 있지만, 합성 방식은 머티리얼 단위라 따로 못 만듭니다. 씬 A(가산) → 씬 B(일반)로 넘어가면 색만 옛것인 어정쩡한 상태가 됩니다. 파티클당 3 float를 더 내고 절반만 푸는 거래입니다 |
| **전환 시 파티클 즉시 제거** | 색도 안 튀고 재할당도 없지만, "씬 전환 중 이펙트 생존" 검증 항목이 사라집니다 |

### C-3. 오버플로 기본 정책 — 가장 오래된 것을 회수 *(사전 확인)*

**근거** 새 타격의 피드백은 항상 보여야 합니다. 부하가 걸릴수록 자기 공격의 피드백을 잃는 쪽이 게임에서는 더 나쁩니다.
슬롯이 다 찬 상황 자체가 비정상이라, 그 상황에서 무엇을 지킬지 고르는 문제입니다.

**고르지 않은 대안** 새 버스트를 통째로 무시(`drop-burst`). 구현해 두고 디버그 패널에서 바꿀 수 있습니다.

### C-4. dt 클램프 — 상한 0.1초 *(사전 확인)*

**문제** 탭을 다른 곳에 뒀다가 돌아오면 `dt`가 몇 초로 찍히고, 파티클이 한 프레임 만에 화면 밖으로 날아갑니다.

**선택** `dt = min(dt, 0.1초)`.

**근거** 절대 폭발하지 않습니다. 시뮬레이션 시간이 실제보다 뒤처지지만 수명이 1초 남짓이라 체감이 없습니다.
0.1초는 실제로 일어날 수 있는 최악의 정상 프레임(무거운 씬 전환, 가비지 컬렉션 정지) 근처입니다.

**고르지 않은 대안**

| 대안 | 탈락 사유 |
| --- | --- |
| **남은 시간을 모아 여러 번 나눠 계산** | 복귀 첫 프레임에 계산이 몰려 p95를 오염시킵니다. 측정이 산출물인 과제에서 측정을 망가뜨리는 최적화는 잘못된 선택입니다 |
| **튄 프레임을 통째로 건너뜀** | 20fps짜리 정상 구간에서도 오작동합니다 |

### C-5. 씬별 렌더러 설정 — 씬은 선언만, 적용은 하네스

**선택** 배경색, 톤 매핑과 노출, 픽셀 밀도 상한을 씬이 값으로 선언만 합니다.

**근거** WebGL 컨텍스트는 하나뿐인 전역 상태입니다. 두 씬이 직접 쓰면 "누가 마지막에 썼는가"가 화면을 결정해 전환 순서에 따라 그림이 달라집니다.
선언으로 바꾸면 전환 시점 한 곳에서만 상태가 바뀝니다.

**고르지 않은 대안** 씬마다 컨텍스트를 따로 두기. 격리는 완벽하지만 브라우저 컨텍스트 개수 제한에 가까워지고 GPU 메모리를 두 배 씁니다.

### C-6. 픽셀 밀도 — 씬이 상한을 정하되, 사람이 고르면 그 상한을 무시

**선택** 기본값은 `min(기기 값, 씬 상한, 하드웨어 상한 2)`. 패널에서 명시적으로 고르면 `min(고른 값, 하드웨어 상한 2)`.

**근거** 씬 A는 상한 2, 씬 B는 1.5입니다(밝은 배경 + 일반 합성이라 오버드로우 부담이 큼).
상한이 다르면 두 씬의 FPS를 그대로 비교할 수 없는데, 사람이 고른 값까지 씬 설정에 막히면 "같은 밀도로 맞춰 비교"가 불가능해집니다.
씬 설정은 기본값이지 측정하는 사람을 막는 장치가 아닙니다.

### C-7. 씬 자원 해제 — 등록한 것만

**근거** 씬 그래프를 순회하며 지우면 씬에 붙은 모든 것을 지웁니다. 이펙트도 그 순간 씬에 붙어 있지만 하네스 것입니다.
등록제(`Disposables`)는 이 사고가 구조적으로 일어날 수 없습니다.

### C-8. 계기는 렌더 루프가 아니라 조작에 즉시 반응

**선택** 씬 전환·부하 변경·비정상 상황 버튼 직후에 계기를 한 번 즉시 갱신합니다. 초당 4번 주기 갱신은 그대로 둡니다.

**근거** 루프가 멈춰 있는 동안(백그라운드 탭) 버튼을 눌러도 숫자가 그대로면,
"리셋이 안 먹은 것"과 "먹었는데 표시만 안 바뀐 것"을 구분할 수 없습니다. 계기를 못 믿으면 그 아래 숫자를 전부 못 믿습니다.
검증 중에 실제로 만난 문제입니다.

**고르지 않은 대안** 갱신 주기 단축. 루프가 멈춘 동안은 주기가 아무리 짧아도 갱신 횟수가 0입니다.

### C-9. 「부하·관측 리셋」의 범위

**선택** 부하 목표뿐 아니라 dt 최댓값 표시와 프레임 표본까지 초기화합니다. 버튼 이름도 「부하 리셋」에서 바꿨습니다.

**근거** dt 최댓값 행은 관측값을 붙잡아 두는 칸이라, 리셋이 부하만 되돌리면 그 칸을 푸는 방법이 씬 전환밖에 없습니다.
비정상 상황을 눌러본 뒤 리셋하는 사람은 깨끗한 기준선을 원합니다.

**되돌리지 않는 것** 이미 발사된 파티클과 누적 드롭·재활용 횟수. README 비정상 상황 절에 표로 분리했습니다.

### C-10. 클릭 발사 — 레이캐스트는 씬 그래프 전체, 이펙트는 스스로 빠짐

**배경** 처음에는 발사가 타이머뿐이라 인터랙티브 이펙트가 아니었습니다. 모듈 API(`burst(point)`)는 처음부터 위치·방향을 받았으므로
빠진 것은 하네스의 입력 배선이었습니다.

**선택** 클릭 좌표에서 레이를 쏘고 `scene.children` 전체에 재귀 교차 검사를 합니다.
맞은 지점과 면 법선(월드 좌표, 레이와 마주 보게 뒤집음)을 `EmitPoint`에 채워 `burst()`를 부릅니다.
이펙트 루트는 모듈 쪽에서 `raycast`를 빈 함수로 덮어써 검사 대상에서 빠집니다.

**근거** 씬 계약에 항목을 추가하지 않기 위해서입니다. "씬이 아는 것은 3가지"가 중심 주장이고, 넷째를 넣으면 약해집니다.
이펙트가 스스로 빠지는 이유는 "파티클은 피킹 대상이 아니다"가 모듈의 성질이기 때문입니다.
하네스가 골라내게 하면 하네스가 `Points`를 알아야 하고 B-2가 깨집니다.

**고르지 않은 대안**

| 대안 | 탈락 사유 |
| --- | --- |
| **씬 계약에 `pickables: Object3D[]` 추가** | 정확하지만 씬이 아는 것이 4가지가 되고 두 씬 파일을 고쳐야 합니다. 메시가 수천 개인 씬이 생기면 그때 갑니다 |
| **하네스가 이펙트 루트를 걸러냄** | "이펙트는 피킹 안 됨"이라는 규칙이 모듈 밖에 놓여, 모듈을 다른 프로젝트로 옮기면 따라가지 않습니다 |
| **`Raycaster.layers`로 거름** | 레이어는 렌더 컬링에도 쓰이는 전역 자원이라 씬이 레이어를 쓰기 시작하면 충돌합니다 |
| **허공 클릭 시 카메라 앞 고정 거리에 발사** | 항상 반응하지만, 충돌이 없는데 파편이 나오면 "충돌 지점 파편"이라는 정의를 어깁니다. 빗나감은 로그만 남깁니다 |

**실측으로 드러난 것** 렌더 루프가 멈춘 채 씬을 바꾸고 첫 프레임 전에 클릭하니,
씬 B 지면이 회전 전 상태로 검사되어 `거리 0.0m · 법선 (0, 0, 1)`로 맞았습니다.
카메라는 `lookAt()`이 월드 행렬을 갱신하지만 메시는 첫 렌더 전까지 단위 행렬입니다.
레이캐스트 직전에 `camera.updateMatrixWorld()`와 `scene.updateMatrixWorld()`를 부르도록 고쳤습니다. 비용은 클릭당 씬 노드 수(약 100)에 비례합니다.

### C-11. 자동 발사는 기본 꺼짐

**선택** 시작 상태에서 클릭 발사만 켭니다. 「자동 발사」 체크박스, 「풀 고갈」 버튼, 부하 스윕이 켜고, 스윕은 끝나면 되돌립니다.

**근거** 첫 화면이 "클릭한 곳에서 터진다"여야 인터랙티브 이펙트라는 전제가 화면에서 증명됩니다.
자동 발사가 켜진 채면 초당 92회 버스트 속에서 클릭 1회분(24개)은 구분이 안 됩니다.

**대가** 「생존 / 목표 N」 행이 `0 / 2,000`처럼 보여 고장처럼 읽힐 수 있습니다.
그래서 「상태」 행에 `클릭 발사만` / `자동 발사`를 표시하고, bursts/s는 꺼져 있으면 0을 보여줍니다.

**고르지 않은 대안** 자동 발사를 켠 채 시작하고 클릭을 N배로 부풀림.
「클릭 발사 누적」과 `stats.burstsRequested`의 1:1 대응이 깨져 계기가 거짓말을 하게 됩니다(C-8과 같은 이유).

## D. 측정

### D-1. "동시 N개"의 정의 — 살아있는 파티클 수 *(사전 확인)*

**문제** 과제 지문 "수명 L초 버스트를 초당 N/L회"는 버스트 한 번이 파티클 한 개일 때만 성립합니다. 이 모듈은 한 번에 24개를 뱉습니다.

**선택** N을 "어느 순간에나 살아있는 파티클 수"로 정의하고 역산합니다.

```
L = 파티클 수명(초),  P = 버스트당 파티클 수
정상 상태에서 초당 생성 = 초당 소멸
살아있는 수 = 초당 버스트 × P × L
→ 초당 버스트 = N / (L × P)          (P = 1이면 지문의 N/L과 같다)
```

**근거** 지문 그대로면 살아있는 수가 목표의 24배가 됩니다. 목표 32,000이라 적어놓고 768,000개가 날아다니는 셈입니다.
정의가 맞다는 증거는 결과표의 실측 생존입니다. 목표 32,000에 31,696(99.0%).

### D-2. 시간을 세 갈래로 나눠서 잼

| 계열 | 무엇을 재나 |
| --- | --- |
| **프레임** | 화면 한 장이 나오기까지 전체 시간 (GPU와 주사율 대기 포함) |
| **CPU 프레임** | 그중 우리 JS가 일한 시간 |
| **이펙트 CPU** | 그중 파티클 적분만 |

**근거** 하나로 합치면 "느리다"까지만 알고 다음에 뭘 고쳐야 할지는 못 고릅니다.

- 프레임 ≫ CPU → GPU 병목
- CPU ≈ 이펙트 → 적분을 GPU로 옮길 근거
- CPU ≫ 이펙트 → 파티클은 죄가 없음

**나중에 검사를 하나 더 넣어야 했습니다.** 실제 GPU에서 파티클 32,000개까지 프레임이 평균 16.67 / p95 16.80ms로 주사율에 딱 붙어 있었습니다.
위 규칙만으로는 프레임과 CPU의 차이가 크니 "GPU 병목"으로 읽히지만, 실제로는 한계 근처에도 못 간 상태입니다.
"더 못 올린다"와 "아직 안 밀어봤다"가 같은 문장으로 읽힌다면 계기의 결함입니다.
그래서 **프레임 p95가 평균의 1.05배 이내**이면서 **CPU가 프레임의 40% 미만**이면 "주사율 고정, 한계 미도달"로 따로 답하게 했습니다.
이 검사 덕분에 상한을 두 번 올려 실제 무릎(약 50만 개)을 찾았습니다.

### D-3. p95 (p99가 아니라)

**근거** 표본이 240개(60fps × 4초)뿐이라 p99는 가장 느린 두세 개 표본이 통째로 결정합니다.

평균도 같이 보는 이유는 실측에서 드러났습니다. `평균 0.211ms / p95 0.152ms`인 줄이 있었는데,
가비지 컬렉션이 몇 번 끼어들어 평균만 끌어올린 것입니다. p95만 봤으면 못 봤고, 평균만 봤으면 "4배 느려진다"고 잘못 읽었을 것입니다.

### D-4. 부하 스윕 — 렌더 루프가 굴리고, 표가 거짓말을 못 하게 함

**선택** 매 프레임 호출되는 상태 기계(`LoadSweep.tick(dt)`)입니다. 여기에 세 가지를 붙였습니다.

- 단계마다 실제로 잰 프레임 수를 표의 「프레임 수」 열에 남깁니다.
- 스윕 중에는 씬·오버플로·픽셀 밀도·비정상 상황 버튼을 잠급니다.
- 중간에 취소되면(하네스 폐기 등) 부분 결과를 돌려주지 않고 실패로 끝냅니다.

**근거** 타이머는 렌더와 어긋난 시각에 깨어나 "3초간 측정"이 프레임 한가운데서 시작하고 끝납니다.
더 나쁜 것은 탭이 뒤로 가면 타이머는 느려질 뿐이지만 `requestAnimationFrame`은 아예 멈춰서, 측정 구간이 한 프레임도 못 재고 끝날 수 있다는 점입니다.
루프가 굴리면 "몇 프레임을 실제로 쟀는가"가 결과에 남고, 그 값이 작은 행의 평균·p95는 통계가 아니므로 독자가 걸러낼 수 있습니다.

나머지 둘은 같은 이유입니다. 스윕 도중 측정 조건이 바뀌면 표의 일부 행이 다른 조건에서 잰 값이 되는데, 그 표는 겉보기에 멀쩡해서 잘못 잰 줄도 모릅니다.
절반짜리 표를 "완료"로 돌려주는 것도 마찬가지입니다. 호출자는 그것이 전체 스윕인지 알 수 없고, README에 붙는 순간 거짓 데이터가 됩니다.

### D-5. 헤드리스 CPU 벤치를 따로 둠

**선택** `npm run bench:cpu`. GPU 없이 고정 dt로 파티클 적분만 잽니다.

**근거** 브라우저 프레임 시간에는 GPU와 주사율 대기가 섞여 기기가 바뀌면 비교가 안 됩니다.
그리고 이 파일이 돌아간다는 사실 자체가 설계의 검증입니다. 이펙트의 적분 경로에 DOM도, window도, WebGL도 필요 없다는 것이 브라우저 밖에서 실행된다는 사실로 증명됩니다.

**실행 방식** `vite build --ssr`로 Node용 번들을 만든 뒤 실행합니다.

| 대안 | 탈락 사유 |
| --- | --- |
| **Node의 타입 제거 실험 기능** | 타입은 떼지만 Node 모듈 해석기가 확장자 없는 `import`를 거부합니다. 전체 `import`에 `.ts`를 붙이면 번들러 설정과 충돌합니다 |
| **esbuild 추가** | 동작하지만 Vite가 이미 같은 일을 하는데 의존성이 하나 늡니다 |

## E. UI와 의존 방향

### E-1. UI 프레임워크 없음

**선택** 헬퍼 함수 4개(`src/ui/dom.ts`)와 디버그 패널 하나가 전부입니다.

**근거** 이 화면이 하는 일은 초당 4번 숫자 20여 개를 다시 쓰는 것뿐입니다.
의존성이 하나 늘면 "`npm install` 한 번으로 구동된다"의 실패 지점이 하나 늡니다.

### E-2. 의존 방향은 한쪽뿐 — UI가 코어를 알고, 그 반대는 아님

**선택** three 타입이 하나도 안 들어간 관측용 타입(`FrameTelemetry`)을 `core/types.ts`에 두고, 패널은 그 타입만 `import type`으로 가져옵니다.

**근거** 콜백만 넘기는 쪽이 이벤트 버스보다 간단하고 타입이 살아 있습니다. 하네스는 UI를 전혀 모르고 `main.ts` 한 곳에서만 둘을 연결합니다.

**확인** `grep -rn "from 'three'" src/ui/` → 0건.

### E-3. `src/shared/` — 작성 도중 발견한 위반의 수정

**선택** 난수 생성기와 직교 기저 계산을 `effects/`에서 `shared/`로 옮겼습니다.

**근거** 씬이 벽 법선으로 평면 기저를 만들 때 `effects/`의 상수와 난수를 런타임 import 하고 있었습니다.
그 두 줄 때문에 "씬이 이펙트에 대해 아는 것은 세 가지뿐"이 문자 그대로는 거짓이 됩니다.
양쪽이 같이 쓰는 수학은 공용 자리로 옮기는 게 맞고, 덤으로 중복이던 기저 계산이 한 곳으로 합쳐졌습니다.

## F. 도구와 환경

### F-1. Vite 6 (7이나 8이 아니라)

**근거** Vite 7과 8은 Node 20.19 이상을 요구합니다. 과제 조건은 "Node 20 이상"인데, Node 20.0\~20.18에서는 설치 단계에서 깨집니다.
Vite 6은 Node 18, 20, 22를 모두 받습니다. "구동 실패 = 평가 불가" 앞에서 최신 버전은 살 가치가 없는 위험입니다.

### F-2. TypeScript 5.9 (7이 아니라)

**근거** 같은 이유입니다. 빌드와 편집기 연동에서 굳이 최신 대형 버전을 감수할 이유가 없습니다.

### F-3. `@types/node` 대신 파일 안에 한 줄 선언

**선택** 헤드리스 벤치 파일 안에 `declare const process: { readonly stdout: { write(text: string): void } }`.

**근거** `@types/node`를 등록하면 브라우저에서 도는 코드에서도 `process.env` 같은 Node 전용 값이 타입 검사를 통과합니다.
결과를 한 줄 출력하겠다고 그 구멍을 만들 이유가 없고, 선언을 직접 쓰면 이 파일이 Node의 무엇을 쓰는지 정확히 문서화됩니다.

### F-4. 안티에일리어싱 끔

**근거** 파티클은 어차피 반투명하게 섞여 그려져 이득이 거의 없고 대역폭만 듭니다. 배경 상자 모서리가 거칠어지는 것은 감수합니다.

### F-5. 씬 배경은 일부러 최적화하지 않음

**선택** 씬 B의 배경 물체 90개를 한 덩어리로 묶지 않고 하나씩 그립니다. 조명은 가장 싼 방식입니다.

**근거** 배경까지 최적화하면 "씬이 가벼울 때만 통하는 수치"가 나옵니다.
배경을 평범한 수준으로 두되 조명은 싼 것을 골라, 병목이 배경이 아니라 이펙트 쪽에 걸리게 했습니다.

### F-6. 유니폼 묶음 타입을 `interface`가 아니라 `type`으로

**근거** three의 머티리얼은 유니폼 묶음에 인덱스 시그니처를 요구하는데, TypeScript는 타입 별칭에만 그것을 자동으로 붙여줍니다.
`interface`로 두면 캐스트가 필요해지고, 그 순간 유니폼 이름 오타를 타입이 못 잡습니다. 코드에도 이유를 남겼습니다.
