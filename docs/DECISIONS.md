갈림길이 있었던 지점마다 **무엇을 골랐는지 / 왜 골랐는지 / 무엇을 왜 버렸는지**를 적은 문서입니다.

작업을 시작하기 전에 네 가지 방향을 먼저 물어봤고, 답을 받은 뒤에 코드를 썼습니다.
그 넷은 아래에서 D-1, C-2, C-3, C-4에 *(사전 확인)* 표시로 붙어 있습니다.

그래픽스를 처음 보는 분도 읽을 수 있게 썼습니다.
줄임말은 쓰지 않았고, `이런 서체`로 표시한 것은 전부 **코드에 실제로 그 이름으로 존재하는 것**입니다.
먼저 용어부터 정리하고 시작합니다.

## 0. 읽기 전에 — 용어 정리

### 화면 한 장이 만들어지는 순서

3차원 장면이 화면에 뜨기까지는 크게 두 단계를 거칩니다.

1. **꼭짓점 계산** — 물체의 꼭짓점(정점)이 화면의 어느 자리에 찍히는지 계산합니다.
2. **픽셀 칠하기** — 그 꼭짓점들이 덮는 화면의 점(픽셀)을 무슨 색으로 칠할지 계산합니다.

이 계산을 하는 작은 프로그램을 **셰이더**라고 부르고, 그래픽 카드 안에서 돌아갑니다.
1번을 맡는 것이 **정점 셰이더**, 2번을 맡는 것이 **프래그먼트 셰이더**입니다.
이 프로젝트에서 파티클(불꽃 알갱이) 하나는 **꼭짓점 하나**이고, 화면에서는 작고 흐릿한 원으로 보입니다.

### 용어표

| 용어 | 뜻 |
| --- | --- |
| **파티클** | 튀는 불꽃 알갱이 하나. 이 모듈은 한 번에 수만 개를 관리합니다 |
| **프레임 / 프레임 타임** | 화면 한 장 / 그 한 장을 만드는 데 걸린 시간. 초당 60장이면 한 장에 16.7밀리초입니다. 밀리초는 1000분의 1초 |
| **중앙처리장치 / 그래픽 카드** | 계산을 맡는 부품 / 화면 픽셀 칠하기를 맡는 부품. 둘 중 어느 쪽이 밀리는지가 이 문서의 핵심 관심사입니다 |
| **셰이더** | 그래픽 카드 안에서 도는 작은 프로그램 (위 설명 참고) |
| **유니폼** | 셰이더에 넘기는 값 중 **모든 파티클이 함께 쓰는 값**. 예: 색, 중력. 바꾸는 비용이 거의 0입니다 |
| **어트리뷰트** | 셰이더에 넘기는 값 중 **파티클마다 다른 값**. 예: 각자의 위치. 파티클 수만큼 메모리를 먹습니다 |
| **버퍼** | 어트리뷰트를 담아두는 큰 배열. 중앙처리장치 쪽 배열의 내용을 그래픽 카드로 **복사(업로드)** 해야 화면에 반영됩니다 |
| **드로우 콜** | "여기부터 여기까지 그려라"라고 그래픽 카드에 보내는 명령 한 건. 건수가 늘수록 중앙처리장치가 명령 준비만 하다 느려집니다. **이 과제는 이펙트의 드로우 콜을 항상 1건으로 유지하는 것이 하드 제약입니다** |
| **합성 방식** | 이미 그려진 화면 위에 새 픽셀을 어떻게 얹을지. **가산**은 색을 더해서 밝아지고(불꽃에 어울림), **일반**은 투명도 비율로 섞습니다 |
| **덧칠** | 같은 픽셀을 여러 번 다시 칠하는 것. 반투명 파티클이 겹칠수록 심해지고, 그래픽 카드 부담의 가장 큰 원인입니다 |
| **화면 픽셀 밀도** | 논리 픽셀 하나를 실제 픽셀 몇 개로 그릴지. 2면 가로·세로 2배이므로 칠할 픽셀이 **4배**가 됩니다. 코드에서는 `devicePixelRatio`라는 이름으로 나옵니다 |
| **적분** | 여기서는 "속도로 위치를 옮기는 계산". 매 프레임 `위치 += 속도 × 흐른 시간`을 파티클 전부에 대해 반복합니다. 흐른 시간(초)을 코드에서 `dt`라고 부릅니다 |

두 가지만 더 있습니다.

- **메모리 자동 정리** — 안 쓰게 된 객체를 브라우저가 알아서 치우는 작업입니다.
  치우는 동안 잠깐 멈추기 때문에 **그 프레임만 툭 튑니다.** 아래에서 자주 나옵니다.
- **평균과 95 백분위수** — 평균은 말 그대로 평균이고,
  95 백분위수는 프레임 100개를 느린 순으로 줄 세웠을 때 **위에서 5번째 자리의 값**입니다.
  "가끔 튀는 프레임"을 잡아내는 값이라, 평균만 봐서는 안 보이는 문제를 드러냅니다.

### 비용을 말하는 방식

"파티클이 몇 개든 항상 같은 시간"과 "파티클 수에 비례해 늘어나는 시간"을 구분해서 씁니다.
앞은 파티클이 10개든 6만 개든 걸리는 시간이 똑같다는 뜻이고, 뒤는 6만 개면 6천 배 오래 걸린다는 뜻입니다.

## A. 이펙트 모듈 내부

### A-1. 파티클 자리 관리 방식 — 원형으로 도는 고정 좌석

**무슨 문제였나** 파티클 6만 개 분량의 자리(슬롯)를 미리 잡아두고 재사용해야 합니다.
새로 터진 파티클에 빈 자리를 내주고 수명이 다한 파티클의 자리는 회수해야 하는데,
이 두 가지가 매 프레임 수백 번씩 일어납니다.

**선택** 좌석이 **원형으로 배치된 극장**처럼 씁니다.
`head`는 가장 오래된 파티클이 앉은 자리, `span`은 거기서부터 몇 자리가 살아있는지입니다.
새 자리는 살아있는 구간 바로 뒤(`(head + span + i) % capacity`)에서 내주고,
자리를 비울 때는 구간 앞쪽부터 죽은 자리를 밀어냅니다.
끝까지 가면 다시 0번 자리로 돌아옵니다.

**근거**

- 자리 내주기와 "가장 오래된 것 회수하기"가 **둘 다 파티클 개수와 무관하게 항상 같은 시간**에 끝납니다.
  이 두 가지를 동시에 만족하는 자료구조는 이것뿐이었습니다.
- 태어난 순서가 좌석 번호 순서와 그대로 일치하므로 "가장 오래된 것"을 **찾아다닐 필요가 없습니다.**
  `head`가 곧 답입니다.
- 살아있는 자리가 항상 **붙어 있는 한 덩어리**라, 그래픽 카드로 복사할 구간이 많아야 두 조각입니다
  (끝을 넘어 0번으로 돌아간 경우에만 두 조각).

**고르지 않은 대안**

| 대안 | 탈락 사유 |
| --- | --- |
| **빈자리 메우기** — 파티클이 죽으면 맨 뒤 파티클을 그 구멍으로 옮겨 앞쪽만 꽉 채우는 방식 | 살아있는 개수만큼만 정확히 그리게 되므로 꼭짓점 계산량 면에서는 원형 방식보다 낫습니다. 그런데 (1) 자리를 옮기는 순간 태어난 순서가 뒤섞여서, "가장 오래된 것 회수"가 **전부 뒤져봐야 하는 작업**으로 바뀝니다. (2) 파티클이 죽을 때마다 버퍼의 아무 곳이나 고쳐 쓰게 되어 복사할 구간이 잘게 조각나고, 결국 매번 전체를 복사하는 쪽으로 되돌아갑니다. 원형 방식의 약점(살아있는 구간 안에 죽은 자리가 섞임)은 A-2의 적응형 그리기 범위로 상당 부분 상쇄됩니다 |
| **빈자리 목록 관리** — 죽은 자리 번호를 따로 목록에 모아두고 거기서 꺼내 쓰는 방식 | 죽은 자리를 정확히 재사용하지만 좌석 순서가 완전히 무작위가 되어, 그래픽 카드로 복사할 구간이 자리 하나 단위로 쪼개집니다. 원형 방식보다 나은 점이 없습니다 |

### A-2. 드로우 콜을 1건으로 지키는 방법 — 그리기 범위를 상황에 맞게 좁힘

**무슨 문제였나** "이펙트의 드로우 콜은 항상 1건"이 하드 제약입니다.
가장 쉬운 방법은 매 프레임 "0번부터 6만 번 자리까지 전부 그려라"라고 한 번 명령하는 것인데,
그러면 파티클이 500개뿐인 순간에도 그래픽 카드가 꼭짓점 6만 개를 계산합니다.

**선택** 살아있는 구간이 배열 끝을 넘지 않으면 그 구간만 그리라고 하고(`setDrawRange(head, span)`),
끝을 넘어 0번으로 돌아간 프레임에만 전체를 그리라고 합니다(`setDrawRange(0, capacity)`).
어느 쪽이든 명령은 **정확히 한 건**입니다.

**근거** 대부분의 프레임에서 꼭짓점 계산량이 살아있는 개수만큼으로 줄어듭니다.
"항상 전체"로 두면 파티클 500개일 때도 6만 개를 계산합니다 — **120배 낭비입니다.**

**고르지 않은 대안**

| 대안 | 탈락 사유 |
| --- | --- |
| **항상 전체 자리를 그림** | 코드는 두 줄 짧아지지만, 부하가 낮을 때 위의 120배 낭비를 그대로 감수하게 됩니다 |
| **끝을 넘어간 프레임만 명령 2건** | 꼭짓점 계산량이 **항상** 살아있는 개수만큼이 되므로 성능상으로는 이게 최선입니다. "드로우 콜 항상 1건"이 하드 제약이라 택하지 않았습니다. **나중에 성능이 문제가 되면 여기가 제일 먼저 풀 매듭입니다.** 지금 방식의 대가는 README의 "알려진 한계"에 실제 측정치로 남겼습니다 |

### A-3. 움직임 계산 — 속도를 먼저 갱신하고, 감속은 지수 함수로

**선택** 속도를 먼저 갱신하고 **그 새 속도로** 위치를 옮깁니다
(정식 명칭은 준음함수 오일러 적분입니다).
공기 저항에 해당하는 감속은 `속도 = 속도 × exp(-저항계수 × dt)`로 계산합니다.

**근거**

- 파티클끼리 서로 밀거나 당기지 않기 때문에, 더 정밀한 계산법을 써도 화면에서 차이가 안 보입니다.
- 지수 함수를 쓰면 흐른 시간 `dt`가 상한(0.1초)까지 튀어도 **속도의 부호가 절대 뒤집히지 않습니다.**

**고르지 않은 대안**

| 대안 | 탈락 사유 |
| --- | --- |
| **`속도 × (1 - 저항계수 × dt)` 로 단순화** | 지수 함수 호출 한 번을 아낍니다. 그런데 `저항계수 × dt`가 1을 넘는 순간 괄호 안이 **음수**가 되어, 파티클이 갑자기 뒤로 날아가 터진 지점으로 되돌아갑니다. 현재 값(저항계수 1.9, 시간 상한 0.1초)에서는 아직 안전하지만 여유가 두 배뿐이라 안심할 수 없습니다. 게다가 지수 함수는 **파티클마다가 아니라 프레임마다 한 번** 계산하므로 비용이 사실상 0입니다 |
| **룽게–쿠타 4차 적분** (훨씬 정밀한 고급 계산법) | 계산량이 3배인데 화면에서 차이가 안 보입니다 |

### A-4. 파티클 모양 — 셰이더로 직접 그림, 이미지 파일 없음

**선택** 프래그먼트 셰이더 안에서 "중심에서 얼마나 떨어졌는가"를 계산해
가장자리가 부드럽게 흐려지는 동그라미를 **그때그때 만들어 냅니다.**
그래픽 카드가 점 하나를 칠할 때 "지금 점 안의 어느 위치를 칠하는 중인지" 알려주는 값(`gl_PointCoord`)을 씁니다.

**근거** 미술의 문제가 아니라 **소유권의 문제**였습니다. 이미지 파일을 불러 쓰면
(1) 불러오기에 실패했을 때의 처리, (2) 그 이미지를 누가 들고 있을지, (3) 두 씬이 같이 쓸 때 누가 치울지 —
세 문제가 한꺼번에 따라옵니다.
"모듈이 만든 그래픽 카드 자원은 모듈이 치운다"는 이 프로젝트의 규칙에 정면으로 걸립니다.
덤으로 아무리 확대해도 깨지지 않고, 저장소에 이미지 파일이 들어가지 않습니다.

**고르지 않은 대안** 여러 모양을 한 장에 모아둔 이미지를 쓰는 방식.
불규칙한 파편이나 연기 얼룩을 못 만드는 것이 대가입니다.
필요해지면 셰이더 안에서 노이즈를 계산하는 쪽이 이미지 도입보다 쌉니다.

### A-5. 무엇으로 그리는가 — 점 하나짜리 도형 한 덩어리 (`THREE.Points`)

**선택** 파티클 하나를 **점 하나**로 그립니다.

**근거** 파티클당 꼭짓점이 1개입니다.
사각형 판을 하나씩 세우는 방식은 파티클당 꼭짓점 4개에 연결 정보까지 필요해 계산량이 4배입니다.

**고르지 않은 대안** 사각형 판 방식(`InstancedMesh`).
회전, 가로세로 비율이 다른 확대, 임의의 그림 좌표를 쓸 수 있지만 이 이펙트에는 회전이 필요 없습니다.
다만 점 하나의 화면 크기에는 그래픽 카드가 정한 상한(보통 1024픽셀)이 있어서,
거기 걸리면 사각형 판으로 갈아타야 합니다.
그 교체가 씬 코드에 안 보이도록 이펙트를 `Object3D`(3차원 물체 일반) 타입으로 내줬습니다 (B-2 참고).

### A-6. 그래픽 카드로 복사하기 — 살아있는 구간만

**선택** 매 프레임 `[head, head+span)` 구간, 즉 **살아있는 자리만** 복사합니다(`addUpdateRange`).
파티클이 새로 태어날 때 필요한 초기값은 실제로 터진 프레임에만 복사합니다.

**근거** 6만 개 전체를 매 프레임 복사하면 **초당 57메가바이트**입니다.
실제로 바뀐 값은 그중 일부뿐입니다.

**주의해야 했던 점** 복사할 구간은 `head`를 앞으로 밀기 **전** 기준으로 잡아야 합니다.
이번 프레임에 죽은 자리의 "수명 0" 표시를 그래픽 카드에 못 올리면,
나중에 좌석이 한 바퀴 돌아 전체를 그리게 되는 순간
그 자리가 **영원히 사라지지 않는 유령 파티클**로 화면에 남습니다.
순서를 반대로 잡았다가 이 함정을 발견하고 고쳤습니다.

**고르지 않은 대안** 매번 전체 복사. 코드는 세 줄 짧지만 위의 대역폭을 그대로 씁니다.

### A-7. 난수 — 시작값을 고정한 간단한 난수 생성기

**선택** `Math.imul(s, 1664525) + 1013904223` —
이전 값에 상수를 곱하고 더한 뒤 잘라내는 고전적인 방식(선형 합동법)입니다.
시작값(시드)을 고정해 둡니다.

**근거** 성능 측정을 두 번 돌렸는데 파티클이 흩어진 모양이 매번 다르면,
프레임 시간의 차이가 **"코드를 고쳐서"** 생긴 것인지
**"이번엔 우연히 파티클이 카메라에 더 가까워서"** 생긴 것인지 구분할 수 없습니다.
**같은 결과가 다시 안 나오는 난수는 측정을 통째로 무의미하게 만듭니다.**
화면 없이 도는 성능 측정에서 생존 수와 그린 자리 수가 재실행해도 한 자리까지 똑같은 것이 이 선택의 증거입니다.

**고르지 않은 대안** 브라우저 기본 난수 `Math.random()`(같은 결과를 다시 만들 수 없음),
mulberry32라는 더 좋은 품질의 생성기(계산량 2배 — 파티클을 흩뿌리는 용도에서는 품질 차이가 눈에 안 띕니다).

## B. 공개 창구 — 모듈이 바깥에 내주는 것

### B-1. 설정을 두 층으로 나눔 — 가르는 기준은 "버퍼를 다시 잡아야 하는가"

**선택**

- **만들 때 정하고 못 바꾸는 것**: 최대 파티클 수, 한 번 터질 때 나오는 개수, 자리가 모자랄 때의 정책, 난수 시작값
  → 읽기 전용, 바꾸는 함수를 아예 두지 않았습니다
- **언제든 바꿀 수 있는 것**: 색, 크기, 수명, 속력, 중력, 감속, 합성 방식 → `setStyle()` 하나로

**근거** 기준을 "자주 바꾸나 / 가끔 바꾸나" 같은 사용 빈도로 잡으면 경계가 흐려집니다.
**버퍼를 다시 잡아야 하는가**는 둘 중 하나로 딱 갈리고, 구현에서 자동으로 검증됩니다 —
바꿀 수 있는 13개 항목이 전부 유니폼이나 움직임 계산의 계수로 흡수되고
버퍼를 건드리는 게 하나도 없다는 사실이, "언제든 바꿔도 된다"는 주장의 증거가 됩니다.

**고르지 않은 대안** 전부 바꿀 수 있게 열어두고 필요할 때 내부에서 버퍼를 다시 잡기.
쓰는 쪽은 단순해지지만 **프레임 도중에 6만 개짜리 버퍼 재할당이 숨습니다.**
호출하는 쪽이 그 비용을 예측할 수 없게 되는 것이 최악입니다.

### B-2. 이펙트를 내줄 때 타입이 "점 덩어리"가 아니라 "3차원 물체 일반"

**선택** 구체적인 구현 타입을 숨기고 `Object3D`로만 내줍니다.

**근거** 내부를 점 방식 → 사각형 판 방식 → 그래픽 카드에서 움직임까지 계산하는 방식으로 갈아끼워도
**씬 코드는 한 줄도 안 바뀝니다.**
점 덩어리 타입 그대로 내주면 누군가 `.geometry.attributes.position` 같은 내부를 만지기 시작하고,
그 순간 교체가 불가능해집니다.

### B-3. 통계 값은 매번 새 객체가 아니라 하나를 재사용

**선택** 내부에 하나 있는 기록 객체를 읽기 전용 형태로 그대로 돌려줍니다.

**근거** 이 통계는 **매 프레임 읽힙니다.** 읽을 때마다 새 객체를 만들면 초당 60개의 쓰레기가 쌓이고,
그걸 치우는 메모리 자동 정리가 **하필 우리가 재려는 바로 그 프레임 시간에 찍힙니다.**
**측정 도구가 측정 대상을 바꾸면 안 됩니다.**

**대가** 쓰는 쪽에서 값을 나중까지 보관하려면 직접 복사해야 합니다. 타입 주석에 명시했습니다.

### B-4. 발사 지점은 새 객체 대신 받은 객체에 채워 넣기 (불변성 규칙의 의도적 예외)

**선택** 씬이 새 좌표 객체를 만들지 않고, 하네스가 건네준 객체의 내용을 채워서 돌려줍니다.

**근거** B-3과 같습니다. 최대 부하에서 초당 1,481번 호출되므로
좌표 객체가 초당 2,962개 생겼다가 버려집니다.
"새 객체를 만들고 원본은 건드리지 않는다"는 규칙의 목적은 **숨은 부작용을 막는 것**인데,
여기서는 건네받은 객체가 호출할 때마다 통째로 덮어써지는 **순수한 출력용 그릇**이라
다른 곳과 값을 공유해서 생기는 문제가 없습니다.
목적은 지키면서 비용만 뺄 수 있는 자리입니다.

## C. 하네스와 소유권

여기서 **하네스**는 씬과 이펙트를 실제로 굴리는 바깥 껍데기(`src/core/App.ts`)를 말합니다.
매 프레임 화면을 그리고, 씬을 전환하고, 창 크기 변화를 처리합니다.

### C-1. 이펙트는 하네스가 하나만 갖고 두 씬이 나눠 씀

**선택** 하네스가 하나 만들어서 지금 활성화된 씬에 붙입니다.

**근거** 씬마다 하나씩 두면 전환할 때마다 실수 배열 6개(약 2.4메가바이트)와
그래픽 카드 버퍼 3개를 새로 잡습니다.
메모리 자동 정리와 버퍼 생성이 겹쳐서 **전환하는 프레임이 수십 밀리초 튑니다.**

**대가와 그 처리** 전환하는 순간 날아가던 파티클이 새 씬으로 딸려 옵니다.
이건 버그가 아니라 위 선택에 붙은 청구서이고, 최대 수명 1.4초 안에 알아서 사라집니다.
README의 비정상 상황 표에 명시했습니다.

**부수 효과 하나** 3차원 물체는 부모를 하나만 가질 수 있어서,
새 씬에서 `add()` 한 번이면 이전 씬에서 자동으로 빠집니다.
하네스가 `remove()`를 따로 부를 필요가 없고, 씬 쪽에 "이펙트 떼어내기" 함수를 만들지 않아도 됩니다.

### C-2. 넘어온 파티클의 색 — 즉시 새 씬 것으로 *(사전 확인)*

**선택** 씬이 바뀌면 색과 합성 방식을 곧바로 새 씬 것으로 교체합니다.
이월된 파티클도 함께 바뀝니다.

**근거** 파티클당 추가 메모리 0, 복사할 데이터 증가 0.
대가는 전환하는 순간 색이 한 번 튀는 것뿐입니다.

**고르지 않은 대안**

| 대안 | 탈락 사유 |
| --- | --- |
| **파티클마다 자기 색을 들고 다니게 함** | 이월된 파티클이 옛 색을 유지할 수 있습니다. 그런데 **합성 방식(가산/일반)은 파티클 단위가 아니라 재질 단위**라 어차피 따로 못 만듭니다. 씬 A(가산) → 씬 B(일반)로 넘어가면 색만 옛것이고 합성은 새것인, 어느 쪽도 아닌 상태가 됩니다. 파티클마다 실수 3개(복사량 60% 증가)를 더 내고 문제의 절반만 푸는 거래입니다 |
| **전환할 때 파티클을 즉시 없앰** | 색이 튀지도 않고 버퍼를 다시 잡지도 않습니다. 다만 "씬 전환 중에도 이펙트가 살아남는다"는 검증 항목 자체가 사라지고, 인스턴스를 하나만 두는 이점의 절반이 날아갑니다 |

### C-3. 자리가 다 찼을 때의 기본 정책 — 가장 오래된 것을 회수 *(사전 확인)*

**선택** 자리가 모자라면 **가장 오래된 파티클을 밀어냅니다.**
반대 정책도 구현해 두고, 만들 때 둘 중 하나로 고정합니다.

**근거** 새로 때린 타격의 피드백은 **항상** 보여야 합니다.
부하가 걸릴수록 플레이어가 자기 공격의 피드백을 잃는 쪽이 게임에서는 더 나쁩니다.
대가는 오래된 파티클이 수명을 못 채우고 사라지는 것인데,
자리가 다 찬 상황 자체가 이미 비정상이라 **그 상황에서 무엇을 지킬지 고르는 문제**입니다.

**고르지 않은 대안** "자리가 없으면 새 타격을 통째로 무시"를 기본으로 하기.
살아있는 파티클은 온전히 수명을 다하지만 새 타격이 아예 안 보입니다.
구현은 해두고 디버그 화면에서 바꿀 수 있게 뒀습니다.

### C-4. 시간이 갑자기 크게 흘렀을 때 — 상한을 0.1초로 자름 *(사전 확인)*

**무슨 문제였나** 탭을 다른 곳에 뒀다가 돌아오면 "지난 프레임에서 지금까지 흐른 시간"이
몇 초로 찍힙니다. 그대로 계산하면 파티클이 한 프레임 만에 화면 밖으로 날아가 버립니다.

**선택** 한 줄짜리 상한: `dt = min(dt, 0.1초)`.

**근거** 절대 폭발하지 않습니다.
탭이 뒤에 가 있는 동안 시뮬레이션 시간이 실제 시간보다 뒤처지지만,
이펙트 수명이 어차피 1초 남짓이라 체감되는 영향이 없습니다.
0.1초를 고른 이유는 **실제로 일어날 수 있는 최악의 정상 프레임**(무거운 씬 전환, 메모리 자동 정리로 인한 정지)이
대략 그 근처이기 때문입니다.

**고르지 않은 대안**

| 대안 | 탈락 사유 |
| --- | --- |
| **자른 뒤 남은 시간을 모아 여러 번 나눠 계산** | 시간 정확도는 올라가지만, 복귀 첫 프레임에 계산이 몰려 중앙처리장치가 튀고 **그게 그대로 95 백분위수를 오염시킵니다.** 측정 결과가 산출물인 과제에서 측정을 망가뜨리는 최적화는 잘못된 선택입니다 |
| **시간이 크게 튄 프레임은 통째로 건너뜀** | 가장 안전해 보이지만, 초당 20프레임짜리 정상 구간에서도 오작동합니다 |

### C-5. 씬별 화면 설정 — 씬은 선언만, 적용은 하네스가

**선택** 배경색, 밝기 압축 방식과 노출값, 픽셀 밀도 상한을 씬이 **값으로 선언만** 합니다.

**근거** 브라우저에서 그래픽 카드를 쓰는 통로(WebGL 컨텍스트)는 **하나뿐이고 전역 상태**입니다.
두 씬이 각자 그 설정을 직접 써버리면 "누가 마지막에 썼는가"가 화면을 결정하게 되어,
**씬을 어떤 순서로 전환했느냐에 따라 그림이 달라집니다.**
선언으로 바꾸면 전환 시점 한 곳에서만 상태가 바뀝니다.

**고르지 않은 대안** 씬마다 그리기 통로를 따로 두기.
격리는 완벽하지만 통로를 두 개 잡습니다.
브라우저가 허용하는 개수 제한(보통 8~16개)에 가까워지고 그래픽 카드 메모리를 두 배 씁니다.

### C-6. 화면 픽셀 밀도 — 씬이 상한을 정하되, 사람이 직접 고르면 그 상한을 무시

**선택** 기본값은 `min(기기 값, 씬이 정한 상한, 하드웨어 상한 2)`.
디버그 화면에서 사람이 명시적으로 고르면 `min(고른 값, 하드웨어 상한 2)`.

**근거** 씬 A는 상한이 2이고 씬 B는 1.5입니다
(씬 B는 배경이 밝고 일반 합성이라 덧칠 부담이 큽니다).
그런데 상한이 다르면 두 씬의 초당 프레임 수를 그대로 비교할 수 없습니다.
사람이 직접 고른 값까지 씬 설정에 막히면
**"같은 밀도로 맞춰 놓고 비교한다"는 조작 자체가 불가능해집니다.**
씬의 설정은 **기본값을 정하는 것이지, 측정하는 사람을 막는 장치가 아닙니다.**

### C-7. 씬이 만든 자원 치우기 — 등록한 것만 치움

**선택** 씬이 직접 만든 도형과 재질만 목록에 등록하고, **등록한 것만** 지웁니다.

**근거** 흔히 쓰는 방식은 씬에 붙은 것들을 전부 순회하면서 만나는 대로 지우는 것인데,
그러면 **씬에 붙어 있는 모든 것**을 지웁니다.
그런데 이펙트도 그 순간 씬에 붙어 있고, 이펙트는 **씬 것이 아니라 하네스 것입니다.**
순회로 지우면 씬을 전환할 때마다 남의 그래픽 카드 자원을 해제하게 됩니다.
등록제는 이 사고가 **구조적으로 일어날 수 없습니다.**

### C-8. 계기는 화면 그리기 루프가 아니라 사람의 조작에 답함

**선택** 씬 전환·부하 변경·비정상 상황 버튼을 누른 **직후에** 계기 값을 한 번 즉시 갱신합니다.
초당 4번 갱신은 그대로 두고 그 위에 얹었습니다.

**근거** 원래는 화면 그리기 루프의 초당 4번 갱신밖에 없었습니다.
그런데 루프가 멈춰 있는 동안(탭을 다른 데 갔다가 돌아온 직후, 창이 가려진 동안)
버튼을 눌러도 화면 숫자가 그대로입니다.
그 상태에서는 **"리셋이 실제로 안 먹은 것"과 "먹었는데 표시만 안 바뀐 것"을
사람이 구분할 방법이 없습니다.**
검증용 화면에서 이건 치명적입니다 — 계기를 못 믿으면 그 아래 숫자를 전부 못 믿습니다.
실제로 검증 중에 이 문제를 만났고, 그래서 고쳤습니다.

**고르지 않은 대안** 갱신 주기를 더 짧게. 근본 해결이 아닙니다 —
루프가 멈춘 동안은 주기가 아무리 짧아도 갱신 횟수가 0입니다.

### C-9. 「부하·관측 리셋」이 되돌리는 범위

**선택** 부하 목표뿐 아니라 시간 최댓값 표시와 프레임 표본까지 함께 초기화합니다.
버튼 이름도 하는 일에 맞게 바꿨습니다(원래는 「부하 리셋」).

**근거** 시간 최댓값 행은 관측된 최댓값을 **붙잡아 두는** 칸입니다
(그래야 상한이 일한 순간이 화면에 남습니다 — A-6 옆 부록 참고).
그런데 리셋이 부하만 되돌리면 그 칸을 푸는 방법이 **씬 전환밖에 없습니다.**
비정상 상황 버튼들을 눌러 본 뒤 "리셋"을 누르는 사람은 깨끗한 기준선을 원하지,
부하만 돌아오고 시간 최댓값과 프레임 표본은 더러운 채로 남기를 원하지 않습니다.

**되돌리지 않는 것** 이미 발사된 파티클(수명을 다 삽니다)과
누적 버림·회수 횟수(인스턴스가 사는 동안의 누적값입니다).
둘은 리셋 대상이 아니라는 것을 README 6절에 표로 분리해 뒀습니다.

## D. 측정

### D-1. "동시 N개"의 정의 — 살아있는 파티클 수 *(사전 확인)*

**무슨 문제였나** 과제 지문은 "수명 L초짜리 버스트를 초당 N/L회 발생시켜라"입니다.
그런데 이 식은 **버스트 한 번이 파티클 한 개를 만들 때만** 성립합니다.
이 모듈은 한 번 터질 때 24개를 뱉습니다.

**선택** N을 **"어느 순간에나 화면에서 살아있는 파티클 수"** 로 정의하고 역산합니다.

```
L = 파티클 수명(초),  P = 한 번 터질 때 나오는 파티클 수

정상 상태에서는 초당 태어나는 수 = 초당 죽는 수 이므로
살아있는 수 = 초당 터지는 횟수 × P × L
→ 초당 터지는 횟수 = N / (L × P)          (P = 1이면 지문의 N/L과 똑같아집니다)
```

**근거** 지문 그대로 두면 살아있는 수가 목표의 **24배**가 됩니다.
목표 32,000개라고 적어놓고 실제로는 768,000개가 날아다니는 셈이라, 숫자가 거짓말이 됩니다.
정의가 맞다는 증거는 결과표의 실측 생존 수입니다 — 목표 32,000에 대해 31,696(99.0%).

**고르지 않은 대안** 지문을 문자 그대로 구현하기. 재현은 되지만 위 이유로 수치가 무의미해집니다.

### D-2. 시간을 세 갈래로 나눠서 잼

**선택** 세 가지를 따로 기록합니다.

| 계열 | 무엇을 재나 |
| --- | --- |
| **프레임** | 화면 한 장이 실제로 나오기까지 걸린 전체 시간 (그래픽 카드와 화면 주사율 대기 포함) |
| **중앙처리장치 프레임** | 그중 우리 자바스크립트 코드가 실제로 일한 시간 |
| **이펙트 계산** | 그중에서도 파티클 움직임 계산만 |

**근거** 하나로 합치면 "느리다"까지만 알고 **다음에 뭘 고쳐야 할지는 못 고릅니다.**

- 프레임이 중앙처리장치 시간보다 **훨씬** 크면 → 그래픽 카드가 병목
- 중앙처리장치 시간이 이펙트 계산과 **비슷하면** → 움직임 계산을 그래픽 카드로 옮길 근거
- 중앙처리장치 시간이 이펙트 계산보다 **훨씬** 크면 → 파티클은 죄가 없음

**나중에 갈래를 하나 더 넣어야 했습니다.**
실제 그래픽 카드(RTX 4070 Ti)에서 재보니 파티클 32,000개에서도
프레임이 avg 16.67 / p95 16.80밀리초로 **화면 주사율에 딱 붙어 흔들리지 않았습니다.**
위 규칙만으로는 이게 "그래픽 카드 병목"으로 읽힙니다. 프레임과 중앙처리장치 시간의 차이가 크니까요.
그런데 실제로는 **아직 한계 근처에도 못 간 상태**입니다. 화면이 초당 60장만 그리므로
남는 시간을 그냥 기다리고 있을 뿐입니다.

"더 못 올린다"와 "아직 안 밀어봤다"는 정반대 상황인데 같은 문장으로 읽힌다면 그건 계기의 결함입니다.
그래서 판정 앞에 검사를 하나 넣었습니다 —
**프레임 p95가 avg의 1.05배 이내**이면서 **중앙처리장치 시간이 프레임의 40% 미만**이면
"주사율 고정, 한계 미도달"로 따로 답합니다.

- 초당 프레임 수만 찍었다면 "32,000개에서 60장 나왔으니 충분"이라고 끝냈을 것입니다.
- 백분위수까지 봤어도 판정을 안 갈랐다면 "그래픽 카드가 한계"라고 잘못 결론냈을 것입니다.

### D-3. 95 백분위수를 씀 (99가 아니라)

**선택** 느린 순으로 위 5%를 잘라낸 자리의 값.

**근거** 표본이 240개(초당 60장으로 4초)뿐이라,
99 백분위수는 사실상 **가장 느린 두세 개 표본이 통째로 결정합니다.** 잡음에 너무 민감합니다.

평균도 같이 보는 이유는 실제 측정에서 드러났습니다 —
`평균 0.211밀리초 / 95 백분위수 0.152밀리초`인 줄이 있습니다.
평균이 더 큰 이상한 경우인데, 메모리 자동 정리가 몇 번 끼어들어 평균만 끌어올린 것입니다.
95 백분위수만 봤으면 못 봤을 것이고,
평균만 봤으면 "여기서 갑자기 4배 느려진다"고 잘못 읽었을 것입니다.

### D-4. 부하 측정은 화면 그리기 루프가 굴림 (타이머가 아니라)

**선택** 매 프레임 호출되는 상태 기계(`LoadSweep.tick(dt)`)로 만들었습니다.

**근거** 타이머는 화면 그리기와 어긋난 시각에 깨어나므로,
"3초간 측정"이 프레임 한가운데서 시작하고 한가운데서 끝납니다.
더 나쁜 것은 **탭이 뒤로 가면** 타이머는 느려질 뿐이지만
화면 그리기 요청(`requestAnimationFrame`, 브라우저가 다음 화면을 그릴 때 불러주는 함수)은 **아예 멈춘다**는 점입니다.
그러면 측정 구간이 **한 프레임도 못 재고** 끝날 수 있습니다.
그리기 루프가 굴리면 "몇 프레임을 실제로 쟀는가"가 결과에 그대로 남습니다.

### D-5. 화면 없이 도는 계산 전용 측정을 따로 둠

**선택** `npm run bench:cpu` — 그래픽 카드 없이, 고정된 시간 간격으로 파티클 계산만 잽니다.

**근거** 브라우저에서 잰 프레임 시간에는 그래픽 카드와 화면 주사율 대기가 섞여 있어,
기기가 바뀌면 비교가 안 됩니다.

그리고 **이 파일이 돌아간다는 사실 자체가 설계의 검증입니다** —
이펙트의 계산 경로에 브라우저 문서 객체도, 창 객체도, 그래픽 카드 통로도 필요 없다는 것이
**브라우저 밖에서 실행된다는 사실로 증명됩니다.**
"내부 구현을 갈아끼울 여지가 있다"는 말이 말뿐이 아니게 됩니다.

**실행 방식** Vite에게 "브라우저용이 아니라 Node에서 바로 실행할 수 있는 형태로 묶어라"라고 시킨 뒤
(`vite build --ssr`) 그 결과를 실행합니다.

| 대안 | 탈락 사유 |
| --- | --- |
| **Node의 타입 제거 실험 기능으로 바로 실행** | 타입 표기를 떼어내는 것까지는 되지만, Node의 모듈 경로 해석기가 확장자 없는 `import`를 거부합니다. 프로젝트 전체의 `import`에 `.ts`를 붙여야 하는데, 그건 번들러 설정과 충돌합니다 |
| **esbuild를 개발 의존성으로 추가** | 동작하지만 의존성이 하나 늡니다. Vite가 이미 같은 일을 하는데 중복입니다 |

## E. 화면 조작부와 의존 방향

### E-1. 화면 조작부에 프레임워크를 안 씀 — 브라우저 기본 기능만

**선택** 헬퍼 함수 4개(`src/ui/dom.ts`)와 디버그 화면 하나가 전부입니다.

**근거** 이 화면이 하는 일은 **초당 4번 숫자 20여 개를 다시 쓰는 것**이 전부입니다.
변경분만 골라 갱신해 주는 프레임워크 기능이 그 일에는 필요 없고,
의존성이 하나 늘면 **"`npm install` 한 번으로 구동된다"의 실패 지점이 하나 늡니다.**
하드 제약이 그 위험을 감수할 이유를 주지 않습니다.

**고르지 않은 대안** lil-gui(three 생태계의 표준 조작 패널이지만 배치를 통제할 수 없고 통계 표시가 어색),
React(이 규모에는 과합니다).

### E-2. 의존 방향은 한쪽뿐 — 조작부가 코어를 알고, 그 반대는 아님

**선택** three 타입이 하나도 안 들어간 관측용 타입(`FrameTelemetry`)을 `core/types.ts`에 두고,
디버그 화면은 그 타입만 가져다 씁니다(실제 코드는 안 가져오고 타입만 가져오는 `import type`).

**근거** "3차원 코드가 화면 조작부를 알지 못하게 한다"를 만족시키는 방법이 두 가지였는데,
콜백 함수만 넘기는 쪽이 이벤트 버스를 두는 쪽보다 간단하고 타입이 살아 있습니다.
하네스는 조작부를 전혀 가져다 쓰지 않고, `main.ts` 한 곳에서만 둘을 연결합니다.

**직접 확인 가능** `grep -rn "from 'three'" src/ui/` → 0건.

### E-3. `src/shared/` 를 새로 만듦 — 작성 도중 발견한 위반의 수정

**선택** 난수 생성기와 직교 좌표축 계산을 `effects/`에서 `shared/`로 옮겼습니다.

**근거** 처음에는 둘 다 이펙트 폴더 안에 있었습니다.
그런데 씬이 벽의 법선(벽에서 수직으로 뻗어 나오는 방향)으로 평면 좌표축을 만들 때
이펙트 폴더의 상수를 가져다 쓰고 있었고, 발사 지점의 난수도 이펙트 폴더에서 가져오고 있었습니다.
**그 두 줄 때문에 "씬이 이펙트에 대해 아는 것은 세 가지뿐"이라는 이 과제의 핵심 주장이
문자 그대로는 거짓이 됩니다.**
양쪽이 같이 쓰는 수학은 공용 자리로 옮기는 게 맞습니다.
덤으로 중복이던 좌표축 계산이 한 곳으로 합쳐졌습니다.

## F. 도구와 환경

### F-1. Vite 6 (7이나 8이 아니라)

**선택** `vite@^6.4.3`.

**근거** Vite 7과 8은 Node 20.19 이상(또는 22.12 이상)을 요구합니다.
과제 조건은 "Node 20 이상"인데, Node 20.0 ~ 20.18에서는 이 둘이 **설치 단계에서 깨집니다.**
Vite 6은 Node 18, 20, 22 이상을 모두 받아들여 20.x 전 구간에서 돕니다.
"구동 실패 = 평가 불가"라는 조건 앞에서 최신 버전은 살 가치가 없는 위험입니다.

### F-2. TypeScript 5.9 (7이 아니라)

**선택** `typescript@~5.9.3`.

**근거** 같은 이유입니다. `npm run dev`는 타입 검사기를 거치지 않으므로 구동에는 영향이 없지만,
빌드와 편집기 연동에서 굳이 최신 대형 버전을 감수할 이유가 없습니다.

### F-3. Node 타입 패키지 대신 그 파일 안에 한 줄 선언

**선택** 계산 전용 측정 파일 안에
`declare const process: { readonly stdout: { write(text: string): void } }` 한 줄을 넣었습니다.

**근거** Node 타입 패키지를 설치하고 설정에 등록하면
**브라우저에서 도는 코드에서도 `process.env` 같은 Node 전용 값이 타입 검사를 통과해 버립니다.**
결과를 화면에 한 줄 출력하겠다고 그 구멍을 만들 이유가 없습니다.
선언을 직접 써두면 이 파일이 Node의 무엇을 쓰는지도 정확히 문서화됩니다.

### F-4. 가장자리 부드럽게 만들기(안티에일리어싱)를 끔

**선택** `antialias: false`.

**근거** 도형 가장자리의 계단을 없애려면 픽셀 하나를 여러 번 표본 추출해야 하는데,
파티클은 어차피 반투명하게 섞여 그려져서 **이득이 거의 없고 대역폭만 그대로 듭니다.**
측정 대상이 이펙트이므로 껐습니다.
배경 상자의 모서리가 거칠어지는 것은 감수합니다(디자인은 평가 대상이 아닙니다).

### F-5. 씬 배경은 일부러 최적화하지 않음

**선택** 씬 B의 배경 물체 90개를 한 덩어리로 묶지 않고 하나씩 따로 그립니다.
빛 계산도 가장 싼 방식을 씁니다.

**근거** 배경까지 최적화하면 **"씬이 가벼울 때만 통하는 수치"** 가 나옵니다.
배경을 평범한 수준으로 두는 편이 측정을 정직하게 만듭니다.
동시에 빛 계산은 일부러 싼 것을 골라서, **병목이 배경이 아니라 이펙트 쪽에 걸리도록** 했습니다.

### F-6. 유니폼 묶음 타입을 `interface`가 아니라 `type`으로 선언

**선택** 타입 별칭(`type`)을 썼습니다.

**근거** three의 재질은 유니폼 묶음에 대해
"아무 이름으로나 접근해도 된다"는 타입 규칙(인덱스 시그니처)을 요구하는데,
TypeScript는 **타입 별칭에만 그 규칙을 자동으로 붙여주고 `interface`에는 안 붙여줍니다.**
`interface`로 두면 타입 검사를 강제로 무시하는 캐스트가 필요해지고,
그 순간 유니폼 이름 오타를 타입이 못 잡습니다.
"객체 모양은 `interface`로"라는 이 프로젝트의 일반 규칙을 어긴 자리라 코드에도 이유를 남겼습니다.
