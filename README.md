# ImpactBurst — 재사용 가능한 Three.js 이펙트 모듈

```bash
npm install && npm run dev
```

브라우저가 자동으로 열립니다 (Vite 기본 포트 5173). Node 20 이상이면 됩니다.
VS Code는 `EffectModuleDemo.code-workspace`를 열면 됩니다.

**설치 없이 보시려면:** <https://29thnight.github.io/EffectModuleDemo/>
`main`에 푸시될 때마다 GitHub Actions가 `npm run build`(타입 검사 포함)를 돌려 배포합니다.
성능 수치를 보실 거라면 로컬 실행을 권합니다 — 배포본도 같은 코드지만,
측정값은 결국 그걸 돌린 기기의 성능이라 평가자 본인 기기에서 재는 편이 의미가 있습니다.

| 명령 | 하는 일 |
| --- | --- |
| `npm run dev` | 개발 서버 + 브라우저 자동 실행 |
| `npm run build` | `tsc --noEmit` 후 프로덕션 빌드 |
| `npm run typecheck` | 타입 검사만 |

## 이 과제에서 실제로 풀려고 한 문제

파티클을 예쁘게 그리는 것이 아니라, **씬이 이펙트에 대해 알아야 하는 것을 최소화하는 것**입니다.
그래서 이 README도 "무엇을 만들었나"보다 "무엇을 숨겼고 왜 그렇게 갈랐나"에 지면을 씁니다.

선택이 갈렸던 지점들의 근거와 탈락한 대안은 [docs/DECISIONS.md](docs/DECISIONS.md)에 항목별로 있습니다.

## 1. 씬이 이펙트에 대해 아는 것 — 정확히 3가지

`src/core/types.ts`의 `SceneModule`이 계약 전부입니다.

### (1) `scene.add(effects.object3D)` — 두 씬에서 문자 그대로 동일한 한 줄

```ts
// src/scenes/IndoorScene.ts:79   그리고   src/scenes/OutdoorScene.ts:81
attachEffects(effectRoot: Object3D): void {
  this.scene.add(effectRoot)
}
```

인자 타입이 `Points`가 아니라 `Object3D`인 것이 요점입니다.
내부 구현이 `Points`든 인스턴싱 `Mesh`든 `Group`이든 이 줄은 바뀌지 않습니다.

씬 전환 시 하네스가 `remove()`를 부르지 않는다는 점도 봐주세요.
`Object3D`는 부모가 하나뿐이라 새 씬에서 `add()` 한 번이면 이전 씬에서 자동으로 빠집니다.
씬이 알아야 할 것이 하나 줄었습니다.

### (2) "어디서 터지는가"

```ts
getEmitPoint(target: EmitPoint): EmitPoint
```

씬이 좌표와 방향만 채워서 돌려줍니다. 씬 A는 벽·바닥 패널 위의 한 점과 안쪽 법선을,
씬 B는 카메라 진행 방향 앞쪽 지면과 `+Y`를 줍니다.
**언제** 터질지는 씬이 모릅니다 — 하네스의 `EmissionScheduler`가 정합니다.

새 객체를 만들지 않고 하네스가 넘긴 `target`을 채우는 이유는,
초당 수백 개의 `Vector3` 쓰레기가 그대로 p95 프레임 타임에 찍히기 때문입니다.
측정이 산출물인 과제에서는 전역 불변성 규칙보다 무할당이 우선입니다.

### (3) "어떻게 보여야 하는가" — 선언만, 적용은 하네스

```ts
readonly effectStyle: EffectStylePatch   // 선언
```

씬은 `setStyle()`을 부르지 않습니다. 하네스가 씬 활성화 시점에 적용합니다.
씬 B의 선언 한 줄이 이 분리의 존재 이유를 그대로 보여줍니다:

```ts
blending: 'normal',   // 밝은 배경에서 가산 합성은 배경보다 밝아질 수 없어 거의 안 보인다
```

### 검증: 씬의 `update`/`dispose`에 이펙트 코드 0줄

```ts
// IndoorScene — 정지 씬이라 몸통이 비어 있다
update(_dt: number, _elapsed: number): void {}

// OutdoorScene — 카메라 이동만
update(_dt: number, elapsed: number): void {
  this.orbitAngle = elapsed * OUTDOOR_ORBIT_SPEED
  this.placeCamera()
}

// 두 씬 공통 — 자기가 만든 것만 회수
dispose(): void {
  this.disposables.disposeAll()
}
```

씬이 `effects/`에서 가져오는 것은 **타입뿐**입니다. 직접 확인할 수 있습니다:

```bash
grep -n "effects/" src/scenes/*.ts
# 전부 `import type` 입니다. 런타임 심볼은 0개.
```

> 작성 중에 실제로 이게 깨졌었습니다. 씬이 벽 법선으로 평면 기저를 만들 때
> `effects/constants`의 `BASIS_FALLBACK_THRESHOLD`와 `effects/rng`의 `createLcg`를
> 런타임 import 하고 있었습니다. 두 줄 때문에 위 주장이 문자 그대로는 거짓이 되므로,
> 공용 수학을 `src/shared/`로 옮겼습니다.

## 2. 공개 API는 두 층 — `src/effects/types.ts`

### 층 1 · 생성 시 고정 (`ImpactBurstConfig`)

바꾸면 GPU 버퍼를 다시 잡아야 하는 값들입니다.
setter를 두면 프레임 중간에 재할당이 숨어버리므로 **타입으로 잠갔습니다**.

| 항목 | 왜 여기 있나 |
| --- | --- |
| `capacity` | 슬롯 총량. 바꾸면 `Float32Array` 6개와 GPU 버퍼 3개를 새로 잡아야 한다 |
| `particlesPerBurst` | 링 할당 단위. 바꾸면 진행 중인 링의 슬롯 정렬이 깨진다 |
| `overflow` | 정책마다 슬롯 회수 경로가 달라 런타임 전환은 거짓말이 된다 |
| `seed` | 중간에 바꾸면 측정 재현성이 사라진다 |

디버그 패널에서 오버플로 정책을 바꿔보면 로그에 이렇게 남습니다:

```
오버플로 정책을 'drop-burst'로 바꾸며 이펙트 인스턴스를 재생성했습니다.
```

재생성이 일어난다는 사실을 감추지 않는 것이 이 API의 요점입니다.

### 층 2 · 런타임 변경 (`EffectStyle`)

색 2종 · 크기 2종 · 수명 · 수명 편차 · 속력 · 속력 편차 · 분사각 · 중력 · 감쇠 · 알파 · 합성 방식.

13개 항목이 전부 **유니폼 또는 머티리얼 상태**(`src/effects/burstMaterial.ts`)
아니면 **CPU 적분 계수**로 흡수되고, 버퍼를 건드리는 항목이 하나도 없다는 것이
"런타임 변경 가능"이라는 주장의 실제 근거입니다.

### 절대 공개하지 않는 것

`ShaderMaterial` · `BufferGeometry` · `BufferAttribute` · `Float32Array` ·
링 커서(`head` / `span`) · `THREE.Points` 인스턴스.

전부 CPU 적분을 GPU 적분으로 갈아끼울 때 사라지거나 형태가 바뀌는 것들입니다.
공개하는 순간 교체가 파괴적 변경이 됩니다.
`src/effects/ParticleBuffers.ts`를 따로 뺀 이유도 같습니다 —
GPU 적분으로 옮기면 `velocities`/`ages`/`lifespans`가 사라지고 부동소수점 텍스처 두 장이 들어오는데,
**바뀔 파일과 안 바뀔 파일이 갈려 있어야** 그 교체가 실제로 가능합니다.

## 3. 자원 소유권

| 주체 | 소유 | 회수 |
| --- | --- | --- |
| `ImpactBurst` | geometry, material, 6개 `Float32Array` | `dispose()`에서 전부. 부모에서 스스로 빠지는 것 포함 |
| 씬 | 자기가 만든 geometry / material | `Disposables`에 등록한 것만 |
| `App`(하네스) | 이펙트 **인스턴스**, renderer | 앱 종료 시 |

씬은 이펙트 자원을 **절대** 해제하지 않습니다.
`scene.traverse()`로 순회하며 지우는 흔한 방식을 쓰지 않은 이유가 정확히 이것입니다 —
그 순간 이펙트 루트도 씬 그래프에 붙어 있고, 이펙트는 씬 것이 아닙니다.
그래서 `src/scenes/Disposables.ts`로 "내가 등록한 것만 내가 지운다"로 뒤집었습니다.

### 인스턴스를 하네스가 갖는 대가

씬마다 이펙트를 두면 전환 때 60,000 슬롯짜리 버퍼가 새로 할당됩니다.
그래서 하네스가 하나만 갖고 두 씬이 공유합니다. **씬 전환 시 재할당 0회.**

대가는 **전환 시점에 살아있던 파티클이 새 씬으로 넘어온다**는 것입니다.
버그가 아니라 위 선택의 청구서이고, 최대 수명(1.4초) 안에 자연 소멸합니다.
유니폼은 즉시 교체되므로 이월 파티클도 새 씬 색으로 바뀌어 전환 순간 색이 한 번 튑니다.
(파티클별 색 attribute를 두면 옛 색을 유지할 수 있지만, 합성 방식은 머티리얼 단위라
어차피 분리할 수 없어 절반만 해결하면서 파티클당 3 float를 더 씁니다. 그래서 택하지 않았습니다.)

## 5. 성능 측정

### 먼저 "동시 N개"를 정의합니다

과제 지문의 "수명 L초 버스트를 초당 N/L회"는 버스트 1회가 파티클 1개일 때만 성립합니다.
버스트가 P개를 뱉으면 정상 상태 생존 수가 `N × P`가 되어 목표를 P배 초과합니다.
그래서 **N을 "동시에 살아있는 파티클 수"로 정의**하고 역산합니다:

```
정상 상태에서 초당 생성 = 초당 소멸
alive = burstsPerSecond × P × L
→ burstsPerSecond = N / (L × P)          (P = 1이면 지문의 N/L과 동일)
```

`src/core/EmissionScheduler.ts`에 이 식 그대로 들어 있습니다.
정의가 맞는지는 결과의 **실측 생존** 열이 증명합니다 — 목표 32,000에 대해 31,696 (99.0%).

### 방법

- 단계마다 **워밍업 1.5초 후 3초 측정**. 워밍업은 정상 상태 도달(수명 1회분)과
  셰이더 컴파일·첫 버퍼 업로드를 측정에서 빼기 위한 것입니다.
- 부하는 2배씩 증가. 로그 축에서 기울기(비용이 선형인지 제곱인지)를 바로 읽기 위해서입니다.
- 난수는 고정 시드 LCG. 두 번 돌렸을 때 파티클 분포가 달라지면
  프레임 차이가 "코드 때문"인지 "이번엔 파티클이 카메라에 더 가까웠기 때문"인지 구분할 수 없습니다.
- **평균 FPS만 기록하지 않습니다.** 세 계열을 따로 잽니다:

| 계열 | 무엇 | 읽는 법 |
| --- | --- | --- |
| 프레임 | rAF 콜백 간격 (vsync·GPU 포함) | 화면에 실제로 나온 프레임 타임 |
| CPU 프레임 | 우리 JS가 돈 시간 | `프레임 ≫ CPU` → GPU 병목 |
| 이펙트 CPU | 그중 파티클 적분만 | `CPU ≈ 이펙트` → GPU 적분 전환의 근거 |

이 구분이 없으면 "느리다"까지만 알고 "다음에 뭘 고칠까"는 못 고릅니다.

### 결과 A — 헤드리스 CPU 적분 (`npm run bench:cpu`)

GPU·버퍼 업로드·드로우 콜을 전부 뺀 순수 CPU 비용입니다. 고정 dt 16.67ms.
용량 60,000 / 버스트당 24개 / `recycle-oldest` / L = 0.9s.

| 목표 N | 실측 생존 | draw 슬롯 | 이펙트 CPU avg | p95 | max | 재활용 | 드롭 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 500 | 495 | 650 | 0.020 ms | 0.027 ms | 0.144 ms | 0 | 0 |
| 1,000 | 987 | 1,311 | 0.026 ms | 0.027 ms | 0.194 ms | 0 | 0 |
| 2,000 | 1,973 | 2,638 | 0.027 ms | 0.032 ms | 0.067 ms | 0 | 0 |
| 4,000 | 3,955 | 5,297 | 0.051 ms | 0.054 ms | 0.136 ms | 0 | 0 |
| 8,000 | 7,927 | 10,625 | 0.211 ms | 0.152 ms | 16.944 ms | 0 | 0 |
| 16,000 | 15,839 | 35,914 | 0.281 ms | 0.367 ms | 8.580 ms | 0 | 0 |
| 32,000 | 31,696 | 56,135 | 0.464 ms | 0.730 ms | 1.314 ms | 0 | 0 |

읽을 점 세 가지:

1. **CPU 적분은 병목이 아닙니다.** 동시 32,000개에서 0.46ms — 60fps 예산(16.7ms)의 3%입니다.
   비용은 생존 수에 거의 정확히 선형입니다(4,000→32,000, 8배 부하에 9.1배 시간).
   즉 **지금 시점에 GPU 적분으로 옮길 근거는 없습니다.** 옮겨봐야 0.46ms를 버는 것이고,
   대신 디버깅 난이도와 코드 복잡도를 크게 지불합니다.
2. **avg > p95인 줄이 있습니다**(8,000: avg 0.211 / p95 0.152). max가 16.9ms인 것과 같은 원인 —
   GC 정지 몇 번이 평균을 끌어올린 것입니다. p95만 봤다면 못 봤을 것이고, 평균만 봤다면
   "8,000부터 갑자기 4배 느려진다"고 잘못 읽었을 것입니다. 두 값을 같이 봐야 하는 이유입니다.
3. **실측 생존과 draw 슬롯 열은 재실행해도 한 자리까지 동일합니다.** 고정 시드 LCG + 고정 dt의 결과이고,
   이 재현성이 없으면 위 1번 결론을 믿을 수 없습니다.

| 32,000 | 31,701 | 55,399 | 1481.5 | 60.0 | 16.67 | 16.80 | 1.37 | 1.80 | 0.91 | 1.40 |

드롭·재활용은 전 구간 0입니다(용량 60,000 안에서 끝났습니다). 도구가 자동으로 붙인 해석:

> - 최대 부하(동시 32,000개)에서 프레임 avg 16.67ms / p95 16.80ms
> - 그중 우리 JS가 1.37ms, 이펙트 CPU 적분이 0.91ms (CPU 시간의 67%)
> - 프레임 − CPU 간극 15.30ms
> - 병목 판정: **vsync 고정(약 60Hz). 이 부하 범위에서는 한계에 도달하지 못했다** —
>   진짜 상한을 보려면 부하를 더 올리거나 vsync를 꺼야 한다.

**이 표에서 가장 중요한 것은 FPS 열이 아니라 프레임 p95 열입니다.**
전 구간에서 avg 16.67ms / p95 16.80ms — 32,000개를 띄워도 **한 프레임도 예산을 넘기지 않았습니다.**
즉 이 하드웨어에서 스윕 범위 전체가 여유 안에 들어오고, **상한을 찾지 못했습니다.**

이 구분이 처음에는 잡히지 않았습니다. 초기 판정 로직은 "프레임 − CPU 간극이 크면 GPU 병목"이라고만
말했고, 이 결과에 대고 `GPU(프래그먼트 오버드로우) 또는 vsync 대기`라는 애매한 답을 냈습니다.
그런데 둘은 전혀 다른 상황입니다 — 하나는 "더 못 올린다"이고 다른 하나는 "아직 안 밀어봤다"입니다.
그래서 판정에 vsync 고정 검사를 넣었습니다(`프레임 p95 ≤ avg × 1.05` 이면서 `CPU < 프레임 × 0.4`).
지금 출력이 그 결과입니다.

읽을 점:

- **CPU 쪽은 부하에 선형입니다.** 이펙트 CPU 적분 0.01 → 0.91ms (N 0 → 32,000).
  16.67ms 예산의 5.5%이고, 브라우저 타이머 해상도(0.1ms) 위에서 측정된 값입니다.
- **`draw 슬롯` 열은 신뢰하지 마세요.** N=4,000에서 5,502인데 N=8,000에서 27,091입니다.
  부하가 2배인데 5배가 나오고, 결정적으로 도는 헤드리스 벤치에서는 같은 조건이 10,625입니다.
  원인은 링 버퍼가 배열 끝을 걸치는 구간이 측정 창(3초)보다 긴 주기로 지나가기 때문입니다.
  아래 "알려진 한계"에 자세히 적었습니다.
- **씬 B는 더 무겁습니다.** 밝은 배경 + 일반 합성이라 프래그먼트 비용이 큽니다.
  DPR 상한도 1.5로 다르므로, 씬 간 비교는 패널에서 DPR을 같은 값으로 고정한 뒤에 하세요.


### 직접 재현하는 법

1. `npm run dev`
2. 좌측 패널에서 씬을 고릅니다 (씬 간 비교 시 **DPR을 같은 값으로 고정**하세요 —
   씬 A는 프로필 상한 2, 씬 B는 1.5로 서로 다릅니다).
3. **부하 스윕 실행** → 약 40초 (8단계 × 4.5초)
4. **결과 복사** → 마크다운 표가 클립보드로. 그대로 붙여넣으면 됩니다.
5. CPU만 따로: `npm run bench:cpu`

### 「부하·관측 리셋」이 되돌리는 것과 되돌리지 않는 것

프로브를 돌린 뒤 이 버튼을 누르면 무엇이 실제로 복귀하는지 헷갈릴 수 있어 분리해 적습니다.
아래는 프레임을 한 장도 그리지 않은 상태에서 버튼만 눌러 측정한 값입니다.

| 항목 | 리셋 후 | 성격 |
| --- | --- | --- |
| 목표 N | 120,000 → **2,000** | 즉시 복귀 |
| bursts/s | 5,555.6 → **92.6** | 즉시 복귀 |
| dt 관측최대 | 6,016.5ms → **0.0ms** | 즉시 복귀 (래치 해제) |
| 프레임 표본(avg/p95) | **초기화** | 즉시 복귀 |
| 살아있는 파티클 | 1,377개 그대로 | **복귀 대상 아님** — 이미 발사된 것은 수명(최대 1.26초)을 다 산다 |
| 누적 드롭 / 재활용 | 그대로 | **복귀 대상 아님** — 인스턴스 수명 전체의 누적 카운터 |

즉 리셋 직후 화면이 몇 초간 여전히 폭발적으로 보이는 것은 정상입니다.
제어값(목표·발사 속도)은 이미 돌아왔고, 눈에 보이는 것은 잔여물입니다.
「생존 / 목표 N」 행에서 이 둘이 분리되어 보입니다.

`frustumCulled = false`인 이유: 파티클은 월드 좌표로 매 프레임 흩어지므로
바운딩 스피어를 다시 구하려면 `O(capacity)` 순회가 필요합니다.
컬링을 끄는 편이 그보다 쌉니다.

## 8. 알려진 한계와 다음 수순

**지금 상태의 한계**

- **스윕이 이 하드웨어의 상한을 찾지 못했습니다.** 32,000개에서도 프레임 p95가 16.80ms로
  60Hz 예산 안입니다. `LOAD_STEPS`를 더 올리거나 vsync를 끄지 않으면 "어디서 무너지는가"를 알 수 없습니다.
  다만 용량 상한이 60,000이라 단계를 더 올리려면 `capacity`부터 키워야 합니다(생성 시 고정 옵션).
- **draw 슬롯 열이 브라우저 스윕에서 노이즈가 큽니다.** 링이 배열 끝을 걸치는 프레임에는
  `drawRange`를 두 조각으로 나눌 수 없어 전체 용량을 그립니다. 그런데 링이 한 바퀴 도는 주기가
  높은 부하에서 측정 창(3초)보다 길어서, "측정 구간에 감긴 프레임이 얼마나 들어갔나"가 운에 좌우됩니다.
  실측이 그대로 보여줍니다 — N=4,000에서 5,502인데 N=8,000에서 27,091이고,
  같은 조건을 결정적으로 도는 헤드리스 벤치에서는 10,625입니다.
  헤드리스 쪽은 단계마다 인스턴스를 새로 만들어 링 위치가 고정이라 이 문제가 없습니다.
  고치려면 측정 창을 링 주기보다 길게 잡거나, 감긴 프레임만 드로우 콜 2회를 허용하면 됩니다.
- **브라우저의 `performance.now()` 해상도가 0.1ms로 뭉개져 있습니다**(Spectre 완화).
  그래서 브라우저 스윕의 이펙트 CPU 열은 낮은 부하에서 0.01~0.10ms로 계단이 집니다.
  헤드리스 벤치가 0.001ms 단위로 나오는 이유입니다.
- **이펙트가 씬 fog를 따르지 않습니다.** 셰이더에 fog 청크를 넣지 않았습니다.
  지금은 두 씬 다 fog가 없어 문제가 없지만, 넣는 순간 파티클만 안개를 무시합니다.
- **파티클끼리, 그리고 파티클과 지오메트리 간 정렬이 없습니다.** `depthWrite: false`라
  서로 잘라먹지는 않지만 겹침 순서는 링 순서를 따릅니다. 가산 합성에서는 순서가 무관하고,
  일반 합성(씬 B)에서는 이론상 보이지만 파티클이 반투명하고 작아 눈에 띄지 않습니다.
- 번들이 546 kB(gzip 141 kB)입니다. 대부분 three이고, 코드 스플리팅은
  "`npm install` 1회 + `npm run dev` 1회"라는 하드 제약에 아무것도 보태지 않아 하지 않았습니다.

**다음에 손댈 순서와 그 근거**

0. **먼저 상한을 찾습니다.** 지금 측정은 "32,000개까지 60fps"까지만 말하고 그 위를 말하지 않습니다.
   `capacity`를 키우고 `LOAD_STEPS`를 연장해 프레임 p95가 16.67ms를 넘기는 지점을 찾아야
   아래 판단들이 근거를 갖습니다. 그 전까지 나머지는 전부 추측입니다.
1. **그때까지는 아무것도 안 함.** 측정이 말하는 바는 CPU 적분이 32,000개에서 0.91ms
   (16.67ms 예산의 5.5%)라는 것입니다. 여기서 최적화할 곳은 이펙트가 아닙니다.
2. 상한을 찾았을 때 GPU가 병목이면 **먼저 프래그먼트**를 봅니다 —
   파티클 크기 축소, `sizeEnd` 감소, DPR 상한 하향. 오버드로우는 면적에 비례하므로 이게 가장 큽니다.
   지금 뷰포트가 3828 × 1962(약 750만 픽셀)이라는 점도 같이 봐야 합니다.
3. 그 다음이 정점 비용 — 위의 "감긴 프레임만 드로우 콜 2회"입니다.
4. **GPU 적분은 마지막입니다.** CPU 적분이 예산의 30%를 넘길 때 근거가 생깁니다.
   지금은 5.5%이니 한참 남았습니다. 다만 CPU 비용이 생존 수에 선형이므로
   대략 **동시 17만 개** 근처에서 그 30%에 닿습니다 — 그게 이 구조의 CPU 쪽 수명입니다.
   그때 바뀌는 파일은 `ParticleBuffers.ts`와 `ImpactBurst.integrateRun()`이고,
   `types.ts`의 공개 계약과 씬 코드는 한 줄도 바뀌지 않습니다. 그러라고 이렇게 갈랐습니다.
