# ImpactBurst — 재사용 가능한 Three.js 이펙트 모듈

```bash
npm install && npm run dev
```

Node 20 이상. 브라우저가 자동으로 열립니다(포트 5173).
**캔버스를 클릭하면 맞은 지점에서 파편이 튑니다.** 벽·바닥·기둥 어디든, 맞은 면의 법선 방향으로 튑니다.
부하 측정은 패널의 「자동 발사」를 켜거나 「부하 스윕 실행」을 누르면 됩니다.

설치 없이 보기: <https://29thnight.github.io/EffectModuleDemo/>
(`main`에 푸시될 때마다 GitHub Actions가 빌드해 배포합니다.)
성능 수치는 로컬에서 재는 편이 좋습니다. 측정값은 결국 그 기기의 성능이기 때문입니다.

## 1. 인터랙션 — 클릭한 곳에서 터진다

캔버스를 클릭하면 하네스가 그 화면 좌표에서 레이를 쏘고,
맞은 지점과 면 법선을 `EmitPoint`에 채워 `burst()`를 부릅니다.

```
pointerdown → 정규화 화면 좌표 → Raycaster.setFromCamera
           → intersectObjects(scene.children, recursive)
           → hit.point / hit.face.normal(월드 좌표, 레이와 마주 보게 뒤집음)
           → effects.burst(point)
```

레이캐스트는 `src/core/ClickEmitter.ts`, 발사 경로 통합은 `src/core/Emission.ts`에 있습니다.
발사 경로는 두 갈래입니다.

| 경로 | 위치 | 시점 | 용도 | 기본 |
| --- | --- | --- | --- | --- |
| **클릭** | 레이캐스트 히트 | 사용자 | 인터랙션 | 켜짐 |
| **자동** | 씬의 `getEmitPoint()` | `EmissionScheduler`(목표 N에서 역산) | 부하 측정 | **꺼짐** |

두 경로 모두 `effects.burst(point)` 한 줄로 끝나고, 모듈은 누가 불렀는지 모릅니다.
게임 엔진에 붙일 때는 `ClickEmitter`를 "물리 충돌 이벤트 → burst"로 갈아끼우면 되고,
`src/effects/`와 씬 코드는 바뀌지 않습니다.

**레이캐스트 대상은 `scene.children` 전체입니다.** 씬 계약에 "클릭 가능한 메시 목록"을 넷째 항목으로
추가할 수도 있었지만, 아래 2절의 "씬이 아는 것은 3가지"를 지키려고 그러지 않았습니다.
대가는 씬에 붙은 모든 것이 후보가 된다는 것인데, 문제가 되는 건 이펙트 루트 하나뿐입니다.
`THREE.Points`의 기본 `raycast`는 정점 전부를 순회하므로 용량 5,120,000이면 클릭 한 번에 512만 회 검사입니다.
그래서 **모듈이 스스로 빠집니다**(`ImpactBurst` 생성자에서 `points.raycast = noop`).
하네스가 걸러내게 하지 않은 이유는 "파티클은 피킹 대상이 아니다"가 모듈의 성질이지 하네스의 사정이 아니기 때문입니다.

**허공을 클릭하면 발사하지 않고 로그만 남깁니다.** "카메라 앞 10m에 발사"로 보정할 수도 있었지만,
충돌이 없는데 파편이 나오면 "충돌 지점 파편"이라는 정의를 스스로 어기게 됩니다. (DECISIONS C-10)

## 2. 씬이 이펙트에 대해 아는 것 — 3가지

`src/core/types.ts`의 `SceneModule`이 계약 전부입니다.
클릭 발사를 붙이면서 이 계약은 바뀌지 않았고, 두 씬 파일의 diff는 0줄입니다.

### (1) `scene.add(effects.object3D)` — 두 씬에서 동일한 한 줄

```ts
// src/scenes/IndoorScene.ts:79   그리고   src/scenes/OutdoorScene.ts:81
attachEffects(effectRoot: Object3D): void {
  this.scene.add(effectRoot)
}
```

인자가 `Points`가 아니라 `Object3D`인 것이 요점입니다. 내부가 `Points`든 인스턴싱 `Mesh`든 이 줄은 바뀌지 않습니다.
씬 전환 시 하네스는 `remove()`를 부르지 않습니다. `Object3D`는 부모가 하나뿐이라 새 씬에서 `add()` 한 번이면 이전 씬에서 자동으로 빠집니다.

### (2) 어디서 터지는가

```ts
getEmitPoint(target: EmitPoint): EmitPoint
```

씬은 좌표와 방향만 채워서 돌려줍니다. 씬 A는 벽·바닥 위의 한 점과 안쪽 법선을, 씬 B는 카메라 앞 지면과 `+Y`를 줍니다.
**언제** 터질지는 하네스의 `EmissionScheduler`가 정합니다.

새 객체를 만들지 않고 하네스가 넘긴 `target`을 채우는 이유는, 초당 수백 개의 `Vector3` 쓰레기가
그대로 p95 프레임 타임에 찍히기 때문입니다. 측정이 산출물인 과제에서는 불변성 규칙보다 무할당이 우선입니다.

### (3) 어떻게 보여야 하는가 — 선언만, 적용은 하네스

```ts
readonly effectStyle: EffectStylePatch
```

씬은 `setStyle()`을 부르지 않습니다. 하네스가 씬 활성화 시점에 적용합니다.
씬 B의 선언 한 줄이 이 분리의 이유를 보여줍니다.

```ts
blending: 'normal',   // 밝은 배경에서 가산 합성은 배경보다 밝아질 수 없어 거의 안 보인다
```

### 검증: 씬의 `update`/`dispose`에 이펙트 코드 0줄

```ts
// IndoorScene — 정지 씬
update(_dt: number, _elapsed: number): void {}

// OutdoorScene — 카메라 이동만
update(_dt: number, elapsed: number): void {
  this.orbitAngle = elapsed * OUTDOOR_ORBIT_SPEED
  this.placeCamera()
}

// 두 씬 공통 — 자기가 만든 것만 회수
dispose(): void {
  this.disposables.disposeAll()
}
```

씬이 `effects/`에서 가져오는 것은 타입뿐입니다.

```bash
grep -n "effects/" src/scenes/*.ts
# 전부 import type. 런타임 심볼 0개.
```

> 작성 중에 실제로 깨졌던 항목입니다. 씬이 `effects/constants`와 `effects/rng`를 런타임 import 하고 있었고,
> 그 두 줄 때문에 위 주장이 거짓이 되어 공용 수학을 `src/shared/`로 옮겼습니다.

## 3. 공개 API는 두 층 — `src/effects/types.ts`

### 층 1 · 생성 시 고정 (`ImpactBurstConfig`)

바꾸면 GPU 버퍼를 다시 잡아야 하는 값들입니다. setter를 두면 프레임 중간에 재할당이 숨어버리므로 타입으로 잠갔습니다.

| 항목 | 왜 여기 있나 |
| --- | --- |
| `capacity` | 슬롯 총량. 바꾸면 `Float32Array` 6개와 GPU 버퍼 3개를 새로 잡아야 한다 |
| `particlesPerBurst` | 링 할당 단위. 바꾸면 진행 중인 링의 슬롯 정렬이 깨진다 |
| `overflow` | 정책마다 슬롯 회수 경로가 달라 런타임 전환이 성립하지 않는다 |
| `seed` | 중간에 바꾸면 측정 재현성이 사라진다 |

디버그 패널에서 오버플로 정책을 바꾸면 인스턴스를 재생성했다는 로그가 남습니다. 재생성을 감추지 않는 것이 요점입니다.

### 층 2 · 런타임 변경 (`EffectStyle`)

색 2종 · 크기 2종 · 수명 · 수명 편차 · 속력 · 속력 편차 · 분사각 · 중력 · 감쇠 · 알파 · 합성 방식.
13개 항목이 전부 유니폼·머티리얼 상태(`src/effects/burstMaterial.ts`) 아니면 CPU 적분 계수로 흡수되고,
버퍼를 건드리는 항목이 없다는 것이 "런타임 변경 가능"의 근거입니다.

### 공개하지 않는 것

`ShaderMaterial` · `BufferGeometry` · `BufferAttribute` · `Float32Array` · 링 커서(`head`/`span`) · `THREE.Points` 인스턴스.
전부 CPU 적분을 GPU 적분으로 갈아끼울 때 사라지거나 형태가 바뀌는 것들이라, 공개하는 순간 교체가 파괴적 변경이 됩니다.
`src/effects/ParticleBuffers.ts`를 따로 뺀 이유도 같습니다. GPU 적분으로 옮기면 바뀔 파일과 안 바뀔 파일이 갈려 있어야 합니다.

## 4. 자원 소유권

| 주체 | 소유 | 회수 |
| --- | --- | --- |
| `ImpactBurst` | geometry, material, `Float32Array` 6개 | `dispose()`에서 전부. 부모에서 스스로 빠지는 것 포함 |
| 씬 | 자기가 만든 geometry / material | `Disposables`에 등록한 것만 |
| `App`(하네스) | 이펙트 인스턴스, renderer | 앱 종료 시 |

씬은 이펙트 자원을 해제하지 않습니다. `scene.traverse()`로 순회하며 지우는 흔한 방식을 쓰지 않은 이유가 이것입니다.
그 순간 이펙트 루트도 씬 그래프에 붙어 있지만 씬 것이 아닙니다.
그래서 `src/scenes/Disposables.ts`로 "등록한 것만 지운다"로 뒤집었습니다.

**인스턴스를 하네스가 갖는 대가.** 씬마다 이펙트를 두면 전환 때 5,120,000 슬롯(약 205MB)을 새로 할당합니다.
그래서 하네스가 하나만 갖고 두 씬이 공유하며, 씬 전환 시 재할당은 0회입니다.
대신 전환 시점에 살아있던 파티클이 새 씬으로 넘어옵니다. 최대 수명(1.4초) 안에 소멸하고,
유니폼은 즉시 교체되므로 전환 순간 색이 한 번 튑니다. (파티클별 색 attribute는 합성 방식이 머티리얼 단위라
절반만 해결하면서 파티클당 3 float를 더 쓰므로 택하지 않았습니다.)

## 6. 성능 측정

### "동시 N개"의 정의

과제 지문의 "수명 L초 버스트를 초당 N/L회"는 버스트 1회가 파티클 1개일 때만 성립합니다.
버스트가 P개를 뱉으면 생존 수가 N × P가 됩니다. 그래서 N을 **동시에 살아있는 파티클 수**로 정의하고 역산합니다.

```
정상 상태에서 초당 생성 = 초당 소멸
alive = burstsPerSecond × P × L
→ burstsPerSecond = N / (L × P)          (P = 1이면 지문의 N/L과 동일)
```

`src/core/EmissionScheduler.ts`에 이 식이 그대로 있습니다. 정의가 맞는지는 결과의 **실측 생존** 열이 보여줍니다.
목표 32,000에 대해 31,696(99.0%)입니다.

### 방법

- 단계마다 워밍업 1.5초 후 3초 측정. 워밍업은 정상 상태 도달과 셰이더 컴파일·첫 버퍼 업로드를 측정에서 빼기 위한 것입니다.
  실제로 잰 프레임 수는 보고서의 「프레임 수」 열에 남습니다. 탭이 가려져 프레임이 몇 장 안 잡힌 행의 평균·p95는 통계가 아니므로 읽지 않습니다.
  (아래 결과 B 표는 이 열이 추가되기 전 실행이라 열이 없습니다.)
- 부하는 2배씩 증가. 로그 축에서 기울기(선형인지 제곱인지)를 바로 읽기 위해서입니다.
- 난수는 고정 시드. 두 번 돌렸을 때 파티클 분포가 달라지면 프레임 차이가 코드 때문인지 우연 때문인지 구분할 수 없습니다.
- 평균 FPS만 기록하지 않고 세 계열을 따로 잽니다.

| 계열 | 무엇 | 읽는 법 |
| --- | --- | --- |
| 프레임 | requestAnimationFrame 콜백 간격 (주사율 대기·GPU 포함) | 화면에 실제로 나온 프레임 타임 |
| CPU 프레임 | 우리 JS가 돈 시간 | 프레임 ≫ CPU → GPU 병목 |
| 이펙트 CPU | 그중 파티클 적분만 | CPU ≈ 이펙트 → GPU 적분 전환의 근거 |

이 구분이 없으면 "느리다"까지만 알고 "다음에 뭘 고칠까"는 못 고릅니다.

읽을 점:

1. **비용은 생존 수에 선형입니다.** 4,096배 부하에 2,658배 시간. 기울기는 파티클 1,000개당 약 14.4us입니다.
   덕분에 상한을 추측하지 않고 계산해서 정할 수 있습니다.
2. **CPU만으로 60fps가 깨지는 지점이 있습니다.** 1,024,000에서 13.920ms(예산의 83%), 2,048,000에서 29.235ms(175%).
   GPU가 아무리 빨라도 이 구간에서는 프레임이 밀립니다. 상한을 2,048,000으로 잡은 근거이자 GPU 적분 전환의 첫 실측 근거입니다.
3. **실측 생존과 draw 슬롯은 재실행해도 한 자리까지 동일합니다.** 고정 시드 + 고정 dt의 결과이고, 이 재현성이 없으면 1번을 믿을 수 없습니다.

"더 못 올린다"와 "아직 안 밀어봤다"는 정반대 상황이므로 판정에 주사율 고정 검사를 넣었습니다
(프레임 p95 ≤ 평균 × 1.05 이면서 CPU < 프레임 × 0.4). 이 검사가 없었다면 "32,000개에서 60fps 나오니 충분"으로 끝났을 것입니다.

- **CPU 쪽은 부하에 선형입니다.** 이펙트 CPU 적분 0.01 → 40.27ms. 헤드리스 벤치와 같은 직선 위에 있고,
  브라우저 쪽이 약간 더 비싼 것은 버퍼 업로드가 포함되기 때문입니다.
- **draw 슬롯 열은 조심해서 보세요.** 이번 실행은 헤드리스 값과 잘 맞지만, 이전 실행에서는 N=8,000이 27,091로 튄 적이 있습니다.
  링 버퍼가 배열 끝을 걸치는 구간이 측정 창(3초)에 들어가느냐가 운에 좌우되기 때문입니다. 9절에 자세히 적었습니다.
- **씬 B는 더 무겁습니다.** 밝은 배경 + 일반 합성이라 프래그먼트 비용이 큽니다. 픽셀 밀도 상한도 1.5로 다르므로
  씬 간 비교는 패널에서 같은 값으로 고정한 뒤에 하세요.

## 9. 알려진 한계와 다음 순서

**한계**

- **클릭 1회 = 버스트 1회(24개)라 작게 보입니다.** 24개는 부하 측정 단위이지 시각적 단위가 아닙니다.
  클릭을 N배로 부풀리지 않은 이유는 「클릭 발사 누적」 계기와 `stats.burstsRequested`의 1:1 대응을 지키기 위해서입니다.
  크게 보이게 하려면 `EffectStyle`의 크기·속력을 만지는 것이 맞습니다.
- **레이캐스트가 씬 그래프 전체를 훑습니다.** 지금은 씬당 100개 안팎이라 문제없지만, 메시 수천 개인 씬에서는
  씬 계약에 "클릭 대상"을 추가하거나 `Raycaster.layers`로 걸러야 합니다. 그 씬이 없어서 지금은 하지 않았습니다.
- **용량 5,120,000이 기동 시 약 205MB를 잡습니다.** GPU 버퍼 102.4MB + CPU 전용 속도·나이·수명 102.4MB.
  과부하 측정이 목적이라 감수한 비용이고, 모듈을 가져다 쓰는 쪽은 `capacity`를 자기 상한에 맞춰 낮춰야 합니다.
- **부하가 너무 크면 목표 N에 도달하지 못합니다.** 프레임이 dt 클램프(0.1s)보다 길어지면 시뮬레이션이 프레임당 0.1초씩만 진행되어
  측정 구간 안에 정상 상태에 못 이릅니다. 스윕 판정이 `TARGET_REACHED_RATIO`(0.8) 미만인 단계를 「목표 미달」로 걸러내지만,
  그 단계의 측정은 버려집니다.
- **draw 슬롯 열이 브라우저 스윕에서 노이즈가 큽니다.** 링이 배열 끝을 걸치는 프레임에는 `drawRange`를 두 조각으로 나눌 수 없어
  전체 용량을 그립니다. 링이 한 바퀴 도는 주기가 높은 부하에서 측정 창(3초)보다 길어서, 그 프레임이 창에 들어가느냐는 운입니다.
  이전 실행에서 N=8,000이 27,091(헤드리스는 10,625)로 나온 것이 그 예입니다.
  고치려면 측정 창을 링 주기보다 길게 잡거나, 걸친 프레임만 드로우 콜 2회를 허용하면 됩니다.
- **브라우저의 `performance.now()` 해상도가 0.1ms입니다.** 그래서 브라우저 스윕의 이펙트 CPU 열은 낮은 부하에서 계단이 집니다.
- **이펙트가 씬 fog를 따르지 않습니다.** 두 씬 다 fog가 없어 문제는 없지만, 넣는 순간 파티클만 안개를 무시합니다.
- **파티클 정렬이 없습니다.** `depthWrite: false`라 서로 잘라먹지는 않지만 겹침 순서는 링 순서를 따릅니다.
  가산 합성에서는 무관하고, 일반 합성(씬 B)에서는 파티클이 반투명하고 작아 눈에 띄지 않습니다.
- 번들이 546 kB(gzip 141 kB)입니다. 대부분 three이고, 코드 스플리팅은 "설치 1회 + 실행 1회" 제약에 보태는 것이 없어 하지 않았습니다.

**다음 순서**

0. **상한을 찾았습니다.** RTX 2080 Ti에서 60fps 상한은 약 50만 개이고, 그 위의 병목은 GPU가 아니라 CPU 적분입니다.
1. **일반적인 사용 범위에서는 아무것도 안 합니다.** 실제 게임의 동시 파티클은 수천\~수만 개이고,
   그 구간의 이펙트 CPU 적분은 0.03\~1.10ms(예산의 0.2\~6.6%)입니다. 아래 항목은 동시 50만 개를 실제로 요구할 때만 근거가 있습니다.
2. **GPU 적분(TransformFeedback 또는 GPU 텍스처 시뮬레이션)이 1순위입니다.** 상한을 찾기 전에는 "CPU 적분이 예산의 30%를 넘으면"이라는
   조건부였는데, 1,024,000에서 115%, 2,048,000에서 242%로 충족됐습니다. 기울기로 역산하면 동시 약 35만 개에서 30% 선에 닿습니다.
   그때 바뀌는 파일은 `ParticleBuffers.ts`와 `ImpactBurst.integrateRun()`이고, 공개 계약과 씬 코드는 바뀌지 않습니다.
3. **프래그먼트는 그 다음입니다.** 최대 부하에서 프레임 − CPU 간극이 0.58ms라는 것은 GPU가 그리는 데 비용을 거의 안 쓴다는 뜻입니다.
   단 이 결론은 이 뷰포트와 이 GPU에 묶여 있어, 4K 풀스크린이나 내장 GPU에서는 순서가 뒤집힐 수 있습니다.
4. **정점 비용은 마지막입니다.** "걸친 프레임만 드로우 콜 2회"입니다. draw 슬롯이 생존 수의 1.35\~1.81배이므로
   정점 셰이더 호출을 최대 25% 줄일 수 있지만, 병목이 CPU인 이상 프레임 타임에는 거의 나타나지 않습니다.
